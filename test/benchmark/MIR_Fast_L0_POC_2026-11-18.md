# MIR fast-L0 POC — 2026-11-18

## Result

No tested variant meets the goal of substantially faster compilation with acceptable execution performance. The aggressive variants save only 7–9% of reported entry-module compilation time on average, while execution becomes 4.4–5.1× slower. The quality-preserving allocator retains L0 allocation fingerprints and machine-code sizes, but reported entry-module compilation is about 3% slower. None is enabled in ordinary builds.

At the user’s request, `ast-native` was removed from runtime selection, dispatch, Script state, teardown and all build inputs (D8.3.1v3). Its source, integration patch and fixtures are archived in `ast_native/archive/`; stale debug/release objects and archive members were removed. MIR L2 remains the default.

## What was changed

The vendored MIR generator’s L0 pipeline already skips SSA, GVN, copy propagation, dead-store elimination, loop-invariant motion, combining and dead-code elimination. Its remaining analysis includes CFG construction, machine lowering, global liveness, live ranges and register/stack-slot assignment. Arbitrarily deleting those analyses cannot retain the existing allocator’s correctness.

The isolated patch tests three alternatives:

- **`stack`:** bypass global liveness solving, live-range construction and interference/coloring; give every referenced pseudo-register a separate stack home. Retain MIR’s ABI lowering, reload generation and target emitter.
- **`static`:** the same reduced pipeline, but give frequently referenced values exclusive callee-saved register homes; spill the rest. Reserve explicit machine operands, early clobbers and module globals.
- **`compact`:** retain exact liveness, live ranges, allocation ordering and stack-slot coloring. Replace per-program-point occupancy maps with per-location live-point bitmaps; query only words touched by a value and inspect stack conflicts only when a register cannot be assigned.

Tied hardware-register functions retain the original allocator. All measured functions used their requested path. Levels 1–3 use the original allocator regardless of the experimental switch. The patch is under `patches/experiments/mir-fast-l0.patch`, outside the applied vendor-patch set. The builder applies it only to a copied tree under `temp/mir_fast_l0/mir`; no source in `lambda/mir/` was edited.

The initial dense bitmap version of `compact` also preserved allocation fingerprints, but scanned many empty words and unused spill locations. The final version bounds these queries. That improvement reduced its overhead on larger functions, but did not produce a useful overall compilation win.

The aggressive allocators cut the measured liveness/allocation/rewrite phase to about 54–56% of L0, but add spill loads/stores and larger stack frames. The additional machine instructions raise emission cost and runtime cost, erasing much of the compiler saving. Generator phase timings come from one separate instrumented run per row/mode, so they are diagnostic rather than repeated timing estimates.

`compact` had matching per-function 64-bit allocation fingerprints and generated byte counts on all 22 rows, plus identical non-timing output in every measured run. Its ~1% self-time difference is small relative to these short workloads; there is no demonstrated runtime improvement. Its sub-1% RSS difference is also too small to claim a useful memory saving.

## Method, artifacts and validation

Host: Apple M3, 24 GiB RAM, macOS 26.5.2. Unchanged registered workloads: R7RS fib, fibfp, sum, sumfp, tak, mbrot, fft; AWFY nbody, json, deltablue and richards, each typed and untyped. Every mode uses the same release executable with JIT forced, MIR level 0, caching disabled and large-source MIR interpreter fallback disabled. One warmup per mode/row, five cyclically interleaved timing samples, three separate compiler/RSS samples, and one separate generator-phase/code-size/allocation-fingerprint run. Exact normalized stdout equality is required; no workload was edited.

Experimental release SHA-256: `f0a1569808ca46a5e71768e861be8e0716de1b84d5f9b499e3da175f2c8ab13b`. Source commit `ae76dbf6de6917dd2a7b397bd6c211f8d118959b` plus the recorded local changes, including preceding Input/DOM build repairs. [Raw measurements](mir_fast_l0/results_2026-11-18.json) include per-sample output, hashes, MIR volumes, phase records, patch hash and the builder’s vendor-source provenance. The executable and patch remained stable through measurement.

- Normal release build and host-export checks passed. Runtime sources and generated build recipes contain no `ast_native` hooks; the rebuilt executable has no native-emitter symbols.
- Experimental compact L0 passed the existing forced-GC/poisoning gate: **368/368**.
- Experimental compact L0 passed MVP emission/ownership units: **66/66**.
- Four L2-request parity probes matched output, allocation fingerprints, generated lengths and selected optimization levels with the experiment off/on. The experiment was inactive in all of them; nbody retained the existing policy downgrade to L1, while fib, fibfp and deltablue used L2.
- Normal Lambda baseline: **7,598/7,599**. The sole failure is `proc_sync_rtc`: `E405`, optional WebRTC dependency unavailable. No fixture or expected result was changed to mask it.
- Normal Test262 baseline: **40,261/40,261**, zero regressions (2,652 skipped outside the baseline).

These checks qualify the bounded POC, not every platform or every MIR program. The rejected stack/static paths were checked against the benchmark outputs; the broader forced-GC gate was run on compact. Normal release artifacts still link the unmodified vendored MIR library (D8.6.2–D8.6.3, S1.6).

```sh
make build-release-compile
python3 test/benchmark/build_mir_fast_l0.py
python3 test/benchmark/run_mir_fast_l0.py
LAMBDA_EXEC_BACKEND=jit LAMBDA_MIR_OPT_LEVEL=0 LAMBDA_DISABLE_MIR_CACHE=1 \
  LAMBDA_MIR_FAST_L0=compact temp/mir_fast_l0/lambda-mir-fast.exe run test/benchmark/r7rs/fib.ls
```

The evidence favors keeping ordinary L0 for fresh native compilation and L2 for optimized images. This experiment does not show that much faster MIR compilation is impossible; it shows that deleting liveness/allocation work or changing this occupancy representation does not meet the goal on these workloads. Further work should profile the remaining MIR construction, CFG/machine lowering, instruction allocation/copying and code publication costs before choosing another implementation.
