# Lambda directory-scoped I/O transactions

**Draft for review · 2026-11-19.** The directory boundary, payload, actors, successful exit guarantee and default CRDT merge behavior below are settled design decisions. The commit protocol, database representation and notification interface are proposals. `open dir { … }` denotes the intended language construct. Its grammar and API are open.

**Relation to existing rulings.** S12.4.1v3–S12.4.4v4 govern resource lifetime and transaction exit. D11.1.2 and D11.2.1–D11.2.3 govern I/O and host grants. The workspace CRDT defines entry identity, moves, saved revisions and grouped updates. This draft connects those contracts to a selected directory. [Formal semantics](../doc/Lambda_Formal_Semantics.md) · [Formal design](../doc/Lambda_Formal_Design.md) · [Workspace CRDT, §10](Lambda_Design_CRDT_Protocol.md#10-workspace-transactions-and-zip-workspaces)

## 1. Scope and participation

One execution of `open dir { … }` scopes one I/O transaction to the selected directory and its descendants. Lambda Sync can manage several directories. Opening one selects exactly one transaction boundary, even when another managed directory is on the same device.

**CRDT merge is the default language and engine contract for directory I/O transactions.** Lambda automatically merges concurrent committed changes from local apps, remote peers and accepted external edits according to the replicated data type. Replicas that receive the same changes converge on the same state, including any competing revisions the type preserves. Apps implement any stronger business guarantees they require.

| Change made during the block | Participation and consequence |
|---|---|
| Create, move, rename or remove an entry wholly within the directory, or change its content | Participates in the directory transaction. This includes changes made by Lambda functions called from the block. |
| Update user RDB data stored within the directory | Participates alongside file and directory changes. A row update can belong to the same logical commit as a file revision. |
| Move or otherwise change data across the selected directory boundary | Lambda emits a runtime warning. The entire operation executes outside the transaction, including its in-directory effect. On block rollback Lambda attempts compensation where feasible. Either side may retain effects. Another writer may have changed the target in the meantime. |
| Change a target wholly outside the directory | Allowed subject to the caller's existing grants. Lambda emits a runtime warning that the effect is outside the transaction. A successful outside write survives rollback of the block. Another managed directory may independently capture it. |
| Advance a CRDT frontier, record a local commit, or update an installation journal | Lambda automatically manages this private bookkeeping, normally outside the directory and outside the user's view. It supports publication and recovery. The user payload consists of the directory entries, content and user RDB changes. |
| Another app or process changes the directory while the block is open | That change has its own author and history. Other Lambda apps contribute their own transactions. Lambda Sync captures external applications' changes and delivers accepted changes to Lambda apps through the CRDT. |

For example, a block under `orders/` renames `draft.pdf` to `invoice.pdf`, records the file revision in `orders/sales.sqlite`, and appends to `../audit.log`. The rename and SQL update must succeed or roll back together for transactional Lambda readers. The audit append emits a warning and can survive an error on block exit. Automatically rerunning the entire block could append twice.

## 2. Successful exit, installation and rollback

**A successful directory `open` exit guarantees a fully captured local CRDT transaction.** The group includes the effects of every participating nested user RDB transaction, its causal context, and references to locally recoverable payloads. It is ready to merge and sync with other apps and devices, including after a process restart. Lambda retains the information needed to request reversal of the group, including its RDB effects. Working-tree installation and peer delivery may still be pending.

The following publication protocol is proposed.

1. At entry, pin the selected directory identity and the committed version used for transactional reads. Collect in-scope effects privately. An RDB participant must be able to prepare its candidate state without exposing a separately committed user database.
2. On a clean exit, finish return-type admission when applicable. Stage referenced file contents and database changes, pin their recovery dependencies, and validate the transaction participants and their dependencies. Merge concurrent CRDT operations according to their data type. Publish one local commit record referencing the complete group. Each record carries a stable identity that can be looked up after an interrupted reply.
3. Make the complete version available to new transactional readers. Retain enough durable information to resume installation, notify other apps and replicate after restart. If the process stops before publication, recovery discards or reclaims unreferenced staging. If it stops after publication, recovery resumes outstanding work from that commit.
4. Install files and database state into the ordinary working directory using guarded, recoverable steps. Other processes can observe those steps. Send the CRDT group to peers asynchronously. If transfer requires several messages, a receiver must have the prerequisites for the promised view before making the group visible.

Under **S12.4.4v4**, a successful `return`, `break` or `continue` that leaves a transaction scope commits it. An error, failed return admission or cancellation before commit rolls it back. Once publication succeeds, a cancellation or lost reply can leave the caller uncertain of the outcome. The proposed commit lookup lets the caller resolve that uncertainty without repeating outside effects. [Transaction exit semantics](../doc/Lambda_Formal_Semantics.md) · [Existing repository commit and recovery](../lmd/package/sync/LOCAL_REPOSITORY.md)

After successful exit, the proposed rollback mechanism publishes a new compensating CRDT transaction linked to the original. Peers may already have observed the original. Compensation targets its edits, preserves independent later edits, and exposes conflicts when later work depends on the effect being undone. For nested RDB changes, capture enough prior row values or version references to construct and validate compensation against the current database. Define the supported undo window and pin the required history for its duration. [CRDT undo semantics for documents](Lambda_Design_CRDT_Protocol.md#6-atomic-editing-and-undo)

Working-tree installation, notification delivery and remote acknowledgement each have their own progress and failure states. A pinned transactional reader must obtain file contents and SQL results from the same published version even while installation is incomplete. Qualify process-crash and power-loss durability separately for each supported storage configuration.

## 3. The user RDB is the critical participant

A private SQLite repository can publish a directory head atomically. That alone cannot coordinate a second SQLite connection that has already committed a user's invoice row. A crash between the two commits would expose a row for a file revision that never became visible. SQLite also limits the atomicity of transactions across attached databases in WAL mode. A writable database needs an engine-aware capture policy because committed pages can still reside in its WAL. [SQLite WAL](https://sqlite.org/wal.html) · [SQLite online backup](https://sqlite.org/backup.html)

### How a nested SQL scope participates

**Proposed lifecycle.** SQL owns statement execution, read-your-writes and constraint checks. The enclosing directory transaction owns publication. For example, a block for `orders/` stages `invoice.pdf` and enters an SQL scope to insert the corresponding invoice row into `sales.sqlite`.

| Point in the block | What the engine does |
|---|---|
| Enter the SQL scope | Resolve the database's stable entry ID and base revision in the directory snapshot. Enlist one private working version for that database in the parent transaction. A later SQL scope on the same database in this block starts from the parent's latest staged version. |
| Execute and close the SQL scope | Run the statements in a native SQL transaction on the private version. Queries see earlier writes. On clean exit, finish the SQL commit there, including deferred constraint checks, and attach its resulting revision or captured changes to the parent. Other apps still see the previously published invoice and database. |
| Close the directory scope | When all participants succeed, make their payloads recoverable and publish one CRDT group containing the file revision and the database effect. A parent error, cancellation or crash before publication leaves both unpublished. Reclaim private staging during recovery. |
| Receive or install the group | A peer obtains all dependencies and admits the complete group by transaction ID. Its installer applies the database revision or supported logical changes through the database adapter and journals progress. Recovery after a lost acknowledgement recognizes an already applied result. |

Under S12.4.4v4, a failed SQL statement marks its SQLite scope rollback-only even when caught. For a participating scope, the recommendation is to mark the parent rollback-only if that scope fails, including failure during SQL commit. This prevents publishing the PDF after its invoice insert failed. The parent policy is proposed. The existing standalone SQLite scope semantics are specified separately. [Scoped SQLite transactions](Lambda_IO_RDB.md#14-scoped-sqlite-sql-transactions-rdb14v4)

If the directory group has already been published, undo uses a new compensating group (§2). The pinned base revision or recorded original row values supply the prior state. Later changes to the same data can require resolution.

### What the CRDT carries

The representation determines what the engine merges. With database snapshots, the workspace CRDT merges revision references and can retain multiple heads. With logical changes, the engine can merge at row or field granularity.

| Candidate | What the directory commit publishes | Main trade-off |
|---|---|---|
| Versioned database snapshot | Execute SQL on a private consistent database version. Publish its immutable revision with the file changes. Transactional SQL readers open the selected revision. Divergent database revisions remain recoverable alternatives. | Simple atomic publication and preservation of each branch's SQL constraints. Concurrent disjoint row updates can still produce a whole-database conflict. Establish the cost for large databases and a safe installation policy for active external connections. |
| Logical database changes | Capture row and schema changes through the database engine. Publish them in the same group as namespace and file operations. Apply them against an identified database version. | Can merge independent rows. Requires stable row identity, deterministic conflict and schema rules, and a policy for unique keys, foreign keys, triggers and migrations. Replaying arbitrary SQL text on a peer can produce different results. |

The requirement is participation of user RDB data under the selected directory. The supported engines, merge granularity, handling of multiple database files and treatment of external SQL writers remain open. Define one capture authority for each database so a SQL commit and its physical file notifications cannot become two logical edits. The existing SQLite scope reads its own writes and a failed statement makes it rollback-only even if caught. The lifecycle above proposes how to propagate that failure to the enclosing directory scope. [Scoped SQLite transactions, S12.4.4v4](Lambda_IO_RDB.md#14-scoped-sqlite-sql-transactions-rdb14v4)

## 4. Multiple apps, external writers and notifications

Two Lambda apps may start at the same directory version. Each authors its own group. A proposed same-machine design shares a per-directory commit authority across processes, serializes the short publication step and distributes committed CRDT changes to subscribers. User code can run concurrently. Cross-device replicas can commit offline. Two apps reading the same version is normal. If each inserts text at the same position, the text CRDT retains both insertions in a deterministic order. If each creates a file with the same name, the workspace retains both entry IDs and derives distinct names for display. Either outcome can be accepted without retrying the block. [Workspace conflict rules](Lambda_Design_CRDT_Protocol.md#102-moves-lifecycle-and-revisions)

Invoice issuance illustrates an application-owned guarantee. Two offline apps can each observe that invoice number 42 is available and issue it to different customers. A later merge can expose the collision, but both customers already hold the number. An app that promises one global invoice sequence can implement a centralized allocator and obtain the number before issuance. Lambda then replicates the issued invoice through the ordinary directory transaction. The app owns allocation, including its behavior when the allocator is unreachable. [Coordination Avoidance in Database Systems, §5.1](https://www.vldb.org/pvldb/vol8/p185-bailis.pdf)

### One local installer per physical directory

**Proposed engine rule.** On each machine, all Lambda apps using the same target directory submit their committed groups to one local sync coordinator for that directory. It runs a single installation worker. The same rule covers changes from peers, compensating transactions, and installation of participating RDB changes. Disjoint directories can install concurrently.

1. **Identify the target.** The host maps an opened directory's verified filesystem identity to one registered working tree, one private repository and one stable lock object outside the working tree. Alternate path spellings and independent app launches must reach that same registration. Refuse a second independent installer for an overlapping registration until ownership of the shared subtree is defined. Revalidate the root identity before resuming an installation.
2. **Acquire installation ownership.** The coordinator holds an exclusive, kernel-managed interprocess lock on the registered lock object. A second coordinator that finds it held leaves its work queued for the owner. Every Lambda entry point that installs into that tree must go through the owner. A process-local mutex, a PID file or a heartbeat timeout alone cannot exclude a paused process that later resumes. Keep the lock object stable and the handle private for the entire period in which the worker can issue filesystem writes. [Linux exclusive lock semantics](https://man7.org/linux/man-pages/man2/flock.2.html)
3. **Install one journal at a time.** Persist the target CRDT version and expected disk state before applying its steps. If app B commits while the worker is installing app A's version, B's transaction can be captured, merged and acknowledged locally. Its pending installation is recoverable from the committed head. The worker finishes or reconciles the existing journal, then installs the newer merged state. A blocked journal remains visible to subscribers. A second worker cannot bypass it. No installer holds the repository publication lock for the duration of the whole install.
4. **Recover ownership after a crash.** Once the OS releases the dead owner's lock, a successor acquires it, reads the existing journal, and inspects the target of the interrupted step. If the desired bytes are already present, record completion. If the expected prior version remains, retry the guarded write. If a third version is present, preserve it for reconciliation. Resume newer work only after reconciling the interrupted install. A slow or suspended owner retains ownership.

The current sync package has a task owner, repository transactions and a persistent install journal with guarded steps. These are reusable components. The shared physical-root registration and process-wide exclusion described here are a proposed host contract. [Repository access](../lmd/package/sync/repository.ls) · [Journal preparation and resumption](../lmd/package/sync/local.ls) · [Guarded install steps](../lmd/package/sync/installation.ls)

### External writers

Cooperation with external apps is best effort. External writers bypass the Lambda scope. Use filesystem events to identify what to inspect and reconcile against the last accepted disk state. Rescan after missed events or restart. Preserve ambiguous or conflicting captures, including changes that race installation. A missing mount or failed scan cannot establish deletion. Import a stable observation as a CRDT change and notify apps from the accepted commit. An editor's unsaved state keeps its own history. The sync design already specifies this import path and the limits of inferring external save boundaries. [External changes, §6.7](Lambda_Design_Data_Sync.md#67-external-directory-and-file-changes) · [Local filesystem behavior](../lmd/package/sync/LOCAL_REPOSITORY.md#filesystem-behavior-and-current-limits)

### When an external save races installation

Suppose the accepted disk version of `notes.txt` is A. A Lambda transaction commits B, and an external editor saves C from A while B awaits installation. If the installer finds C, it pauses the affected step, captures C durably, and imports it relative to A when that base is established. The CRDT can then merge independent text edits or retain competing revisions for review. If the external editor's base is uncertain, preserve C and B for resolution. The captured transaction for B remains available for sync while installation is blocked. For a live user database, this step requires a database-consistent observation through its engine. [External-edit reconciliation](Lambda_Design_Data_Sync.md#78-external-edits-while-a-document-is-open)

A final race remains if the installer checks A, the editor saves C, and the installer replaces C with B before anyone captures C. A watcher notification or a successful readback of B cannot reconstruct C. An atomic rename publishes a complete file but still replaces an existing destination. A hard guarantee of preserving every external save requires host support that preserves the displaced version or writer coordination covering the race. The current journal guards each step, retains detected competing changes and can report a blocked installation. Its documented limits include the final replacement window and automatic rebasing after partial installation. [Local repository installation limits](../lmd/package/sync/LOCAL_REPOSITORY.md#filesystem-behavior-and-current-limits) · [Linux rename semantics](https://man7.org/linux/man-pages/man2/rename.2.html)

### Change notifications

For notifications, a candidate event carries directory identity, commit identity, causal version and affected entry or database identities. App-originated, peer and external-import changes use the same subscription path. Subscribers can deduplicate by commit identity, resume from a cursor or refresh from a snapshot when history has expired. Define how an app receives its own commits and how it learns that disk installation is blocked. Incoming events leave previously bound Lambda values intact under the existing snapshot rules. [Language integration, §11](Lambda_Design_Data_Sync.md#11-integration-with-lambda)

## 5. Decisions still open

| Decision | Case the design must settle |
|---|---|
| RDB participation and commit point | Choose a database representation and specify atomic local recovery for one file plus one or more user databases. Define what a direct SQL client can observe during installation and how an external write to an open database is captured safely. |
| Isolation and conflicts | Define how apps read and resolve competing revisions preserved by a merge. Specify read-after-write for paths, listings and SQL. Existing document write sets and SQLite have different rules. |
| Root identity and compound operations | Define membership for symlinks, hard links, mount points and roots renamed or replaced mid-block. Set policy for nested configured roots and for opening a subdirectory of a configured root. Specify how to report residual paths after best-effort compensation and how sync captures a surviving in-directory effect. D11.1.2 still governs each resolved target. |
| Scope propagation and diagnostics | Define nesting, child tasks, pre-opened handles, explicit commit/rollback, and unsupported I/O adapters. Decide how to handle a subprocess writing inside the directory. Specify when and where the warning appears for an outside change, including a dynamically resolved path. |
| Delivery and recovery | Choose subscriber ordering, replay, retention and slow-consumer behavior. Define how peers obtain an entire large transaction before publishing it, how to report missing content, and how to resolve interrupted commits and installations. Define compensation retention, RDB constraint failures during undo, and how a caller resolves a dependent later edit. |
| Cost and limits | Set budgets for block duration, staged bytes, database versions, CRDT group size and pinned history. Keep long-running user code, network waits and bulk copying outside the publication lock. Measure contention before adopting finer-grained locking. |

## 6. Acceptance cases

- **Mixed commit and abort.** Rename a file, update an in-root database, and append to an outside log. Check warning delivery, successful commit, handled SQL failure, failed return admission and cancellation. On rollback, the outside append alone survives.
- **Crash recovery.** Stop after staging, after publication but before replying, and halfway through installation. Reopen the directory. Every transactional reader must see a complete version. A lookup by commit identity must resolve an interrupted reply. Resume installation without repeating the logical transaction.
- **Concurrent apps.** Run two processes against the same root. Start both from the same version, create distinct entries with the same name, and verify that both survive with the same resolved names on both replicas. Check that the shared starting version alone never requires either app to rerun its block. Each subscriber must be able to reconstruct the accepted version after a disconnect.
- **Installer exclusion and failover.** Launch two independent app processes through aliases of the same directory. Pause the owner immediately after its first filesystem write and before it records progress. Confirm that the second app can commit and that no second installer writes, even after a heartbeat timeout. Kill the owner, acquire the same lock in a successor, and verify that it recognizes the completed write, finishes the journal and installs the merged result. A third app targeting a disjoint directory can install throughout.
- **Nested SQL publication.** Close a successful SQL scope, reopen the database within the same parent and read the staged invoice row. Verify an independent transactional reader still sees the old revision. Abort the parent and verify that neither the PDF nor its row was published. Repeat with a deferred constraint failure on inner exit and with a successful outer commit that reaches a peer twice.
- **Post-commit rollback.** Sync a mixed file and RDB transaction to a peer, add an unrelated edit on that peer, then request rollback. Verify that compensation propagates as one group and the unrelated edit survives. Repeat with a later edit to the same row and exercise the conflict outcome.
- **External writers.** Exercise editor save-by-replacement, an external SQL commit in WAL mode, and an external write during installation. Inject the editor save both before revalidation and between revalidation and replacement. Record which host primitives preserve the displaced bytes. A blocked install must leave the complete captured transaction available for sync. Exercise watcher overflow and root unmount. Verify that recoverable input survives and the originating install does not return as a duplicate edit.
- **Root confinement.** Configure two directories. Change one file in each from a block targeting the first, then abort. Move a file across the boundary, then abort. Check the runtime warning and exclusion of the entire move from the commit. Exercise successful compensation and compensation blocked by another writer. Verify that sync reconciles the resulting directory state. Check link resolution and host grants.
- **Replication and performance.** Commit offline, send a group larger than one transport frame, interrupt transfer, and reconnect. A peer must see a coherent group. Measure p95 local commit latency, writer-lock time, peak staged bytes and notification lag for a tiny edit in a large directory, many small files and a large user database. Record installation and replication latency separately. [Existing multi-file measurements](impl/Lambda_Impl_Sync_Multifile_Perf.md)
