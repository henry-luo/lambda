# Lambda Impl: LambdaJS Struct and Type Clean-Up

- **Date:** 2026-08-18
- **Status:** PROPOSAL — census and source audit complete; no runtime implementation started. The four first-tier items (P3, P1, P2, P6) plus two banked P5 fixes are designed in [`Lambda_Design_Structs_JS.md`](Lambda_Design_Structs_JS.md) (2026-09-07), which extends this ledger with JSCU9–JSCU24 and JSCUO1–JSCUO7 and re-measures the §2 table.
- **Scope:** LambdaJS runtime, web/Node compatibility state, JS callable representation, and JS compiler records under `lambda/js/`. Shared Lambda data/runtime structures are referenced where LambdaJS should reuse them rather than introduce a second mechanism.
- **Principle:** one concept or mechanism has one authoritative owning struct. A mechanism may have private node/entry records, but it has one public owner and one lifecycle. Distinct language semantics must not be merged merely because their current layouts look alike.
- **Formal authority:** D3.4.7 (immutable JS class metadata), D4.3.3 (precise VMap trace/finalize), D5.1.1/D5.1.3 (side stacks versus non-LIFO heap ownership), D5.4.1–D5.4.4 (canonical context, lazy capsules, reset-as-construction, immutable registries and lock-free hot paths), D6.2.1/D6.2.2v2 (function identity and distinct Call/Construct capabilities), D6.3.1 (one scheduler and ordered jobs), D7.3.5 (Test262/WPT/Node gates), D7.4.1v2 (native carriers and rids), D7.4.5v2 (virtual array/element carriers), and D8.2.1/D8.2.2/D8.2.4/D8.2.5 (unified indexed compilation and typed fact tables).
- **Census artifacts:** `vibe/meta/ds/struct_census.csv` and `vibe/meta/ds/struct_census.json`, generated by `utils/struct_census.py`.
- **Related proposal:** `vibe/Lambda_Proposal_Struct_Clean_Up.md`. Its `StorageDesc`, Shape, callable-code/ABI, `CompilationUnit`, and binding-fact work are shared dependencies, not concepts for LambdaJS to redeclare.
- **ID series:** `JSCU1`–`JSCU8` are this proposal's local rulings. Implementation stages are `P0`–`P9`.
- **Follow-up proposal:** [Lambda_Design_Structs_JS.md](Lambda_Design_Structs_JS.md) continues the series with proposed **JSCU36–JSCU43** for shared Lambda/JS optimization structures and continues definition-level code sharing under **JSCU33(A)**. It is a draft, not an implementation or a revision of a formal ruling.

## 0. Outcome

LambdaJS should converge on these ownership chains:

```text
EvalContext
  -> JsRuntimeState                 small capsule directory
       -> lazy subsystem capsule    one owner, one lifecycle

JsStableRootArray                  one native stable-root mechanism
GC carrier                         preferred owner for object-specific Item edges

JS function value
  -> JsCallableCode                immutable call/construct/code facts
  -> optional bound/class/origin payloads

CompilationUnit + dense IDs
  -> JsFunctionDecl                source identity
  -> FnAnalysis                    capture/effect/type facts
  -> JsFunctionPlan                environment and ABI plan
  -> JsMirFunctionEmitter          transient lowering state

Native resource object
  -> engine internal slots or rid  no context-wide fixed object pool
```

The primary simplification is not renaming 485 declarations. It is removing four repeated structural patterns:

1. `JsRuntimeState` is both a migration capsule and an eager aggregate of unrelated subsystems.
2. Stable GC ownership is implemented as many unrelated fixed arrays, range descriptors, epochs, counters, and hard caps.
3. Generators, async activations, observers, XHR objects, crypto contexts, and live DOM collections are stored in context-wide index pools even though each state belongs to one live object or operation.
4. JS compiler facts are copied among `JsFuncCollected`, `JsMirTranspiler`, branch snapshots, and closure snapshots instead of being ID-keyed authorities.

The target is deliberately not one universal JS state struct. The directory and lifecycle mechanism are shared; realm, event-loop, module, DOM, Node, diagnostic, compiler, and resource concepts retain separate owners.

The census was refreshed with:

python3 utils/struct_census.py -j 1 --top 50

It covered 529 translation units, reused 437 cached units, parsed 92 units, and reported:

The summed sizes of JS records are not a memory-footprint number. Embedded records are counted both independently and as part of their owners; many records are per-operation, lazy, or mutually exclusive. The census is used to locate maximum-capacity storage and overloaded ownership, then each candidate is checked at its allocation, trace, reset, and destroy sites.

Other limits:

- Sizes reflect the current macOS build configuration and alignment.
- Function-local records can appear when clang exposes their declarations, but this is not a complete automatic-stack census.
- Field counts say nothing about whether a record has one coherent lifecycle. A 60-field socket may be one valid resource, while a four-field observer registry can still embed 1.6 MB of unrelated maximum capacity.
- Large generated enums are catalogs, not memory pressure. Their conceptual boundaries must be judged independently of field count.

## 3. Governing consolidation rules

### JSCU1 — One authoritative owner and lifetime

A struct owns one concept when all of its fields are created, reset, traced, and destroyed together for the same reason. Fields with different lifetimes belong in referenced owners even when embedding them would save a pointer.

Examples:

- A Promise and its reactions share one lifetime and may be one GC carrier.
- A realm's builtin identity cache and process-global builtin catalog have different lifetimes and must be separate.
- A generator's suspended environment belongs to the generator object, not to the context that happened to create it.
- Trace events are diagnostics and must not enlarge semantic runtime state (D5.4.4).

### JSCU2 — The public mechanism is singular; private entries are allowed

“One mechanism, one struct” means consumers use one owner and API. A dynamic collection can still have a private block or entry record. Callers must not reproduce its capacity, root-registration, epoch, counter, and cleanup machinery.

### JSCU3 — Capacity is allocation policy, not type layout

Workload-dependent counts do not belong in inline C arrays. Protocol or safety limits remain explicit checked configuration, but their maximum does not determine `sizeof` the parse result, permission policy, observer registry, or runtime context.

### JSCU4 — Precise roots remain precise and address-stable

D5.1.1, D5.1.3, and D5.4.2 prohibit replacing fixed roots with a reallocating buffer whose Item addresses can move. Consolidation must use GC-owned carriers when state naturally belongs to a JS object, the existing LIFO root side stack for lexical lifetimes, or one stable native rooted collection for context-owned non-LIFO Items. Conservative native-stack scanning remains retired.

### JSCU5 — Reset is lifecycle, not a growing clearing checklist

Per D5.4.3, a full batch reset constructs a fresh realm/heap state. A preamble checkpoint is a specific transaction with an explicit snapshot contract. Neither is a generic loop that memset-clears every structure ever added to LambdaJS.

### JSCU6 — Immutable code facts are shared; mutable value state is not

Call/construct entries, native ABI policy, source site and compiled artifact identity belong to immutable callable code. Closure environment, properties, bound arguments, class runtime state and realm identity belong to a function value or optional payload (D6.2.1/D6.2.2v2).

### JSCU7 — Compiler facts are ID-keyed authorities

D8.2.4 and D8.2.5 require dense identities and typed fact tables. AST pointers and copied flags may be temporary migration indexes, but they cannot remain the long-term identity or fact transport between collection, analysis, planning, and lowering.

### JSCU8 — Preserve real semantic distinctions

Consolidate storage and lifecycle mechanisms, not semantics. Section 11 lists structures that must remain distinct.

## 4. Replace `JsRuntimeState` with a capsule directory

### 4.1 Target ownership

`EvalContext` remains the canonical isolate owner and sanctioned TLS root (D5.4.1). Its `js_state` points to a small, stable directory:

```c
struct JsRuntimeState {
    void* capsules[JS_CAPSULE_COUNT];
    uint64_t heap_epoch;
    uint32_t lifecycle_phase;
    uint32_t flags;
};

struct JsCapsuleOps {
    const char* name;
    JsCapsuleLifetime lifetime;
    void* (*construct)(EvalContext* context);
    void (*release_heap)(void* capsule);
    void (*destroy)(void* capsule);
};
```

`JsCapsuleOps` is a frozen process-global descriptor table. The mutable pointers are per context. This is permitted by D5.4.4: immutable registries stay global, while context-dependent values stay in the context. Lifecycle iteration is cold; repeated execution uses compile-time-indexed inline accessors and ordinary pointer loads, with no lock, atomic, or semantic catalog dispatch.

Capsules are allocated lazily and never reallocated during their heap epoch (D5.4.2). A capsule may own dynamic subordinate allocations, but rooted Item storage follows section 5. Examples of coherent capsules include:

- core realm identity and well-known references;
- global binding and constructor caches;
- execution state (`this`, `newTarget`, super/with/eval stacks);
- event-loop queues and timers;
- Promise/unhandled-rejection state;
- module/CommonJS state;
- code artifact store;
- each independent Node module that has mutable realm state;
- each independent web subsystem;
- optional diagnostics and tracing;
- test-only Test262 agent state.

Do not replace the current mega-struct with `JsNodeState` or `JsWebState` mega-structs. A grouping capsule is justified only for shared state with one lifecycle; unrelated `fs`, `crypto`, `http`, DOM observer and XHR storage remain separate slots.

### 4.2 Lifecycle groups

| Lifetime | Examples | Full realm reset | Context destroy |
|---|---|---|---|
| process immutable | builtin catalog, class metadata, bootstrap options | retained | retained until process exit |
| context | capsule directory, scheduler shell, code store if explicitly reusable | retained or explicitly replaced | destroyed |
| realm/heap | globals, constructors, prototypes, module values, DOM wrappers, regex last match | destroyed, then constructed | destroyed |
| execution | call/eval/with/super transient state | must be empty before boundary | destroyed |
| resource | timers, sockets, requests, crypto rids | canceled/finalized by owner contract | canceled/finalized |
| diagnostics | trace buffer, counters | cleared or replaced without affecting semantics | destroyed |

The code store must not be hidden inside realm value state. Use one `JsCompiledArtifact` owner for a MIR context, source owner, module/name image and release operation; `JsCodeStore` owns a dynamic collection of artifacts. This replaces `JsDeferredMirState`'s parallel arrays and makes the decision to preserve compiled preamble code across a realm reset explicit.

### 4.3 Reset contracts

Full batch reset becomes:

```text
quiesce event loop/resources
assert execution state empty
release realm roots and old heap in defined order
destroy realm-lifetime capsules
replace heap/name-pool/module slabs
construct a fresh realm
restore only explicitly retained code/preamble artifacts
```

Preamble reset uses a typed `JsRealmCheckpoint` containing only the module slab IDs/counts, cache epochs, and other state formally promised to survive. It must not call “reset all roots” and then special-case identity anchors. The current exception that skips `builtin_cache.roots` during generic root clearing demonstrates why the transaction needs a named contract.

## 5. One precise stable-root mechanism

### 5.1 Preferred ownership order

Use these mechanisms in order:

1. LIFO value: `RootFrame`/`Rooted` on the precise side stack.
2. State belonging to a JS object: store Items in the GC object/carrier and trace them there.
3. Non-LIFO native capsule state: `JsStableRootArray`.
4. Raw non-Item scalar/POD metadata: ordinary dynamic storage, never scanned as Items.

`JsPromise` is the positive runtime example: it is a GC-owned `VMap`, owns its result and reaction array, and has no context-wide promise capacity. Generator and async state should follow that ownership pattern rather than the old index-pool pattern. VMap trace/finalize must remain allocation-free and non-reentrant (D4.3.3).

### 5.2 `JsStableRootArray`

`JsStableRootArray` is the one public owner for growable native Item roots. Internally it allocates fixed-address blocks, registers each block before publishing its first Item, never moves a block, clears vacated slots, and retains block storage until the owning heap epoch ends. It supports push/pop, indexed lookup, clear, and a high-water diagnostic. It has no workload-visible fixed maximum.

This replaces repeated combinations of:

```text
Item slots[N]
JsRootRange
roots_epoch
count/depth
register-once helper
manual reset callback
```

The first migration set should include eval source/binding journals, CommonJS/with/super stacks, global lexical bindings, readline maps, diagnostics channels, async hooks, AsyncLocalStorage, RAF callbacks, and other fixed root arrays in `js_runtime_state.hpp`.

Where a logical entry contains several Items plus POD metadata, prefer a GC-owned entry object. If native storage is required, keep the precisely scanned Item region separate from same-index POD metadata so the collector never interprets pointers, integers, or flags as Items.

### 5.3 Root registry

Delete the fixed `root_range_registry[64]` and the giant `JS_RUNTIME_ROOT_STORAGE` catalog. Construction of a capsule or stable-root block registers its own explicit range against the owning heap, exactly once per epoch. Lifecycle ownership supplies reset/destroy; a second registry of reset callbacks is unnecessary.

If the GC root API needs unregister support for same-epoch capsule destruction, add that as a precise heap API or retain the registered block until heap replacement. Never free registered storage while its heap can still scan it.

## 6. Move suspended and object-specific state to its owner

### 6.1 Generators

Current state:

- `JsRuntimeState::generators[4096]` stores every `JsGeneratorStateRecord`.
- The visible generator carrier stores a numeric index.
- On exhaustion, `js_generator_create_current` reuses the first completed slot.
- The carrier tracer looks back through the context table to mark the environment, class home, and delegate.

This is both a capacity mechanism and an identity hazard: an older completed carrier can still name a slot later reused by another generator.

Target: one `JsGeneratorState` owned by the generator's internal-slot carrier. It contains the state function/artifact reference, re-homed environment, state number, execution flags, class home, and delegation state. The carrier traces its own edges. There is no context index, pool count, cap, or recycling rule.

D5.1.1 and D5.1.3 require exactly this ownership: suspension is a re-homing boundary and non-LIFO state owns its heap storage.

### 6.2 Async function activations

Current `async_contexts[256]` roots every possible entry individually, binds the numeric index into resume/reject callbacks, and rejects the 257th live activation.

Target: one GC-owned `JsAsyncFrame` per suspended activation. It owns the compiled artifact reference, re-homed environment, state, result Promise, `this`, and module state identity. Resume and reject closures retain the frame Item/internal handle, not a context array index. Completion releases cycles according to the Promise/frame trace contract.

Promise, generator, and async frame remain three distinct state machines. They share heap ownership and precise tracing, not one universal resumable record.

### 6.3 DOM observers

Replace the 64 × 32 observer matrix with:

- one `JsObserver` native/internal-slot owner per observer object;
- a dynamic target collection sized to the targets actually observed;
- one dynamic attribute-filter representation, preferably interned `NameId`/String identities rather than `char[8][64]`;
- a small `JsObserverDeliveryState` capsule containing only the pending-delivery list and scheduled flag.

Mutation, Resize, and Intersection observers can share the delivery/target collection mechanism, but their configuration/sample payloads remain tagged variants because their semantics differ. Native DOM pins and `DomNodeRef` ownership must be released by the observer owner.

### 6.4 XHR and other asynchronous request objects

Replace `JsXhrRuntimeState::pool[64]` with one `JsXhrRequest` owned by each XHR object's internal slots. Request headers use the shared dynamic HTTP field collection from section 7.1. The realm capsule retains only an active-operation list needed for cancellation during reset.

Apply the same test to fetch work, child processes, sockets and TLS objects: if the state is owned by one live JS resource, attach it to that resource or store a rid in the object (D7.4.1v2). A context-wide array is justified only when the context, not the object, is the semantic owner.

## 7. Consolidate maximum-capacity subsystem records

### 7.1 HTTP request parsing

Replace `ParsedRequest` with two concepts:

- `HttpRequestParser`: incremental parse cursor, limits and error state.
- `HttpRequestHead`: method/version/URL/body spans plus header and trailer field lists.

One `HttpFieldSpan` stores offsets/lengths into an owned connection/request buffer and any normalized-name ID/hash needed for lookup. Header and trailer lists use the same field representation. Preserve original spelling, order, duplicates, and raw-header behavior through the source span; do not retain raw and normalized 4 KB copies for every possible slot.

The owning buffer must outlive all spans. Protocol byte/count limits remain explicit parser configuration and fail with the correct HTTP status; they do not become inline array dimensions. The target `HttpRequestHead` is under 256 bytes excluding dynamic fields/body storage, and no request parse path places an 815 KB record on the native stack.

### 7.2 Live DOM collections

`SelectOptionsOwnerEntry` and `LiveChildCollectionEntry` are identical. The form and lookup variants add document/root/query fields, while four 4,096-entry arrays repeat the same issued-collection registry mechanism.

Use one `JsLiveCollectionRegistry` with one tagged `JsLiveCollectionEntry`, keyed by the actual collection identity inputs `(document, root/owner, collection kind, query, include_root)`. Allocate entries dynamically and centralize node pins, weak array homes, refresh depth, invalidation and teardown.

D7.4.5v2 formally points live indexed host data toward `VArray`; the carrier implementation now supersedes this proposal's earlier deferral. Live-by-reading VArray deletes refresh-by-mutation rather than coexisting indefinitely.

### 7.3 Permission policy

The current ownership boundary places `JsPermissionPolicy` in the lazy
`NodeRuntimeSession`; the bootstrap copy remains process-level command-line
configuration until a Node session needs a mutable policy. The representation
cleanup below is still pending.

Replace inline `JsPermissionGrant[128]` arrays with one immutable `JsPermissionPolicy` configuration containing dynamic read/write grant sets. A grant owns one normalized `Str` path plus flags or a compiled prefix entry; normalize once at policy construction.

The bootstrap policy becomes immutable after publication (D5.4.4). `process.permission.drop()` creates a context delta/copy-on-write policy rather than memcpy-copying 263 KB. There is no silent path truncation or 128-grant ceiling. Allocation failure and malformed paths fail closed.

### 7.4 Crypto and other native handles

The current ownership boundary places `JsCryptoNativeState` in the lazy
`NodeRuntimeSession`; crypto namespace objects remain ordinary JS realm state.
The resource-table consolidation below is still pending.

Replace the four 4,096-pointer arrays in `JsCryptoNativeState` by introducing or reusing one runtime native resource/rid-table mechanism. Each entry carries resource kind, native handle and destructor. JS-visible objects store an integer rid, never a raw pointer (D7.4.1v2). Context teardown closes remaining entries through that table.

Hash, HMAC, sign/verify and cipher contexts remain distinct resource kinds; the registry and lifecycle are consolidated, not their algorithms.

### 7.5 Trace events

Make tracing a lazy `NodeTraceBuffer`. Intern category/name strings once and store compact event records such as phase, category ID, name ID, timestamp, optional ID and flags. The events use a configured ring or dynamic buffer. With tracing disabled, the semantic runtime allocates no event array.

Diagnostics must never influence runtime semantics (D5.4.4). Dropping or rotating trace events is therefore a diagnostic policy, not a JS execution branch.

### 7.6 Timers, RAF and event-loop queues

Use dynamic stable registries for timer handles, mock waits and RAF callbacks. Continue using `RuntimeAsyncDeque` as the one queue storage mechanism where its ordering contract fits.

Do not merge nextTick, ECMAScript microtasks, timers, immediates and RAF into one queue. Their checkpoint and phase ordering is observable and constrained by D6.3.1. Consolidate queue storage/handle registration, while retaining named semantic queues.

### 7.7 Deep object-pair traversal

Replace `JsAssertPartialContext` and `JsDeepEqualContext` with one `JsObjectPairTraversal` mechanism. It owns a dynamic precisely rooted pair stack/visited index and accepts an immutable comparison policy for strict equality, partial matching, prototype handling, typed-array policy and error comparison.

The algorithms remain separately named entry points. Only cycle detection, pair ownership and capacity handling are shared. Any property access that may allocate must keep the active pair Items precisely rooted across the call.

## 8. Split callable code from function-value state

`JsFunction` currently combines:

- compiled/native call and construct entries;
- native target, arity and adapter policy;
- source/module/catalog identity;
- closure environment;
- ordinary properties and prototype;
- bound target/`this`/arguments;
- class constructor/prototype/superclass state;
- eval/VM source origin;
- home realm/class and `with` environment;
- a per-value runtime-context pointer.

Target concepts:

| Owner | Facts |
|---|---|
| `JsCallableCode` | immutable Call/Construct entries, native adapter/target, formal signature, static function/site ID, module artifact, source descriptor, catalog link ID |
| `JsFunction` | GC header, `JsCallableCode*`, closure env, ordinary properties/prototype, home realm/class, flags and optional payload reference |
| `JsBoundFunctionData` | bound target, bound `this`, owned argument vector |
| `JsClassFunctionData` | class constructor body, instance prototype, superclass/private-home data |
| `JsEvalOrigin` | VM/eval filename, source and offsets shared only by dynamically compiled functions |

Every function value retains distinct `[[Call]]` and `[[Construct]]` capabilities as required by D6.2.2v2. Catalog IDs and display names remain metadata. The split must preserve the generated function ABI during migration with explicit offset assertions; update all producers and consumers before deleting compatibility fields.

The realm function-identity cache becomes a dynamic precisely rooted table keyed by a typed `JsCallableKey`, not parallel fixed arrays of keys and `JsFunction*`. Explicit catalog aliases still control `===`; sharing one `JsCallableCode` does not imply sharing a function value.

After the D5.4.1 context migration is complete, ordinary function values do not carry `runtime_context`. Truly cross-turn native resources retain their owner through the resource/frame object whose lifecycle requires it.

## 9. Split compiler records into IDs, facts and transient emitters

### 9.1 `JsFuncCollected`

**DONE.** The record is **984 → 96 B** with 13 members, not 58. The original
ruling follows.

Replace the 58-field bag with ID-keyed authorities:

| Table/record | Owns |
|---|---|
| `JsFunctionDecl` | `FunctionId`, AST definition node ID, parent ID, name/body symbol, declaration/class/static/strict flags |
| shared `FnAnalysis` | captures, use/def, effects, return/type facts |
| `JsFunctionPlan` | environment layout, capture slots, arguments plan, native/boxed entry plan, TCO eligibility |
| `JsConstructorShapePlan` | constructor field names/types/parameter sources, allocated only for constructors |
| `JsMirFunctionState` | MIR items/registers/labels active only while lowering one function |

The existing dynamically sized captures and shared `FnAnalysis` are the direction to keep. The four fixed constructor-shape arrays and cached scope-walk hashmaps do not belong in every function record.

### 9.2 `JsMirTranspiler`

**First split LANDED 2026-09-08: `JsMirFunctionEmitter`.** See §14.1 for the
result and the naming trap. The other four records this section names
(`JsMirModuleEmitter`, `JsControlFlowState`, `JsGeneratorLoweringState`,
`JsEvalLoweringState`) are still inline in a 664 B coordinator; the ratchet is
met and further splitting is structure-only.

**Earlier assessment, kept because it still applies to the remaining four:** §9.3 took the record from 30,840 B to
**2,720 B**, so the size argument for the lifetime split is gone. What remains
is the architectural case — D8.2.4/D8.2.5 lifetime hygiene, so that lowering
consumes resolved IDs and facts rather than carrying analysis as mutable
emitter flags — against a five-way split of a ~100-member record that every
lowering file touches. That is the same shape as JSCU25/26: ratified, no
measurable payoff left, high blast radius. It wants an explicit decision rather
than being taken as the next item by default.

The original ruling follows.

Split by lifetime:

- `JsMirModuleEmitter`: MIR context/module, immutable compilation-unit indexes, module name table, function/class IDs and module constants.
- `JsMirFunctionEmitter`: current function, `MirEmitter`, lexical-scope stack, argument frame, error lane and per-function plan.
- `JsControlFlowState`: loop/try/iterator/label stacks.
- `JsGeneratorLoweringState`: resume labels and environment slots, allocated only for generator/async lowering and exact-sized from analysis.
- `JsEvalLoweringState`: eval completion, preamble and direct-eval details, allocated only for eval/module paths that need them.

This follows D8.2.4/D8.2.5: lowering consumes resolved IDs/facts and does not repair binding or preserve analysis as mutable emitter flags. The shared `VarEntry` cleanup belongs to `vibe/Lambda_Proposal_Struct_Clean_Up.md`; LambdaJS should consume the shared binding identity/location/fact split rather than typedef and extend another 46-field authority.

### 9.3 Closure tracking and branch checkpoints

The same 512-capture shape currently appears in:

- `JsMirTranspiler::last_closure_*` parallel arrays;
- `JsMirClosureTrackerSnapshot`;
- `JsMirLastClosureSnapshot`;
- `JsMirBranchState`.

The two snapshot structs are layout-equivalent 7,696-byte copies; branch state adds the same arrays plus cloned lexical-scope maps.

**LANDED 2026-09-08.** `JsClosureCapture` (name, binding, slot, and the three
flags) replaces the six parallel arrays, and `JsClosureTracker` holds them in a
grow-on-demand list. A save is a **mark into a transpiler-owned journal**, not a
copy: `jm_save_last_closure_snapshot` pushes the live captures and records where
they start, `jm_restore_last_closure_snapshot` copies them back and truncates to
the mark. That choice matters because every snapshot is a stack local at six
call sites with multiple return paths — a snapshot owning its own allocation
would leak on any early return, whereas the journal is owned by the transpiler
and freed once in `jm_destroy_mir_transpiler`.

`JsMirTranspiler` 30,840 → 19,088 B, `JsMirLastClosureSnapshot` 11,792 → 16 B,
`JsMirBranchState` 11,864 → 80 B. The 512-capture ceiling is gone, and with it a
real source-language limit: `jm_last_closure_track_count` used to silently drop
capture read-back past 512, so a closure mutating more than 512 outer bindings
lost the write-back. Verified with a 700-capture closure, which now reads back
correctly. Gates: test262 40261/40261 with 0 regressions, JS gtest, script gtest,
rooting core, MIR GC stress, callable catalog, lambda baseline 5077/5077 (the
memtrack gate), node slice identical to pristine, radiant baseline at its five
pre-existing failures.

The original ruling follows.

Introduce one dynamic `JsClosureTracker` containing exact-sized `JsClosureCapture` records. Branching uses a small `JsClosureCheckpoint`/scope-journal mark and restores by rollback, not by copying 512 possible entries. One save/restore implementation serves statements, expressions and conditional branches.

**LANDED 2026-09-08, and it was a correctness fix, not a size one.**
`gen_state_labels` was a fixed 64-entry array, and two clamps existed to match
it: `if (yield_count > 63) yield_count = 63;` for generators and the identical
line for `await_count` in async functions. Both truncated **silently**. A
generator with 100 yields summed only its first 62 values — it returned 1891
instead of 4950 — and a 150-await async function was wrong the same way. No gate
caught this: test262, the JS suites and the node slice all passed with the bug
present, because nothing in them has more than 62 suspension points in one
function. The label array is now exact-sized from the pre-counted state count,
`jm_next_resume_state` checks the real capacity instead of a literal 64, and
both clamps are deleted. Verified: 100-yield generator, 200-yield async
generator and 150-await async function all produce correct results.

`tdz_closure_captures[512]` (16,384 B, 86 % of what was left of
`JsMirTranspiler`) also grows on demand now; `JsMirTranspiler` is
**30,840 → 2,720 B** across §9.3.

The original ruling follows.

Generator resume-label arrays are exact-sized from the pre-counted yield count. Property-name caches and other small bounded optimization caches may remain bounded only when overflow has a correct generic path and measurements justify inline storage; they must not impose a source-language limit.

### 9.4 Compilation-unit alignment

`JsTranspiler` should become the JS front-end view of the shared indexed `CompilationUnit`, not a parallel source/CST/AST/scope owner. D8.2.1/D8.2.2 retain JS extension nodes only for semantics that cannot use the core catalog. `FunctionId`, `ClassId`, `ScopeId`, `BindingId` and `NodeId` replace AST pointer identity in cross-pass data.

## 10. Builtin catalogs, class metadata and generated IDs

`js_builtin_catalog.def` is already a good single source. It generates related target, binding and global records and has structural gates. Preserve this architecture.

Do not merge these merely to lower enum count:

- `JsBuiltinId`: executable/catalog target identity.
- `JsBuiltinOwner`: property installation group.
- `JsBuiltinGlobalId`: realm global binding identity.
- `JsConstructorId`: constructor cache slot.
- `JsClass`: runtime object brand/family.

Where a relation among them is invariant and one-to-one, generate the lookup from the catalog rather than hand-maintaining another table. The concepts remain typed separately so an owner ID cannot accidentally select executable semantics (D6.2.2v2).

`JsClassMeta`/property operation tables also remain immutable static metadata under D3.4.7. Mutable realm prototype Items and caches stay in realm capsules, never in `TypeMap` or static metadata. Construction-only catalog hash indexes can be exact-sized/generated rather than fixed-capacity as the catalog grows, but they do not participate in ordinary property reads.

## 11. Structures that must not be collapsed

| Keep distinct | Reason |
|---|---|
| Call entry and Construct entry | distinct per-callee capabilities required by D6.2.2v2 |
| Promise, generator and async frame | different state machines and ownership edges; only heap/root primitives are shared |
| nextTick, microtask, timer, immediate and RAF queues | observable ordering and phase semantics (D6.3.1) |
| ordinary Map object and engine internal-slot VMap | representation and property model differ (D7.4.1v2) |
| materialized Array and live `VArray` | D7.4.5v2 is the separate carrier contract |
| runtime class brand, catalog target, builtin owner, global binding and constructor cache ID | different identities used at different stages |
| immutable builtin catalog and mutable realm cache | process versus realm lifetime |
| semantic `Type*`, representation plan, `MirValue`, MIR register type | separate authorities under D8.2.5 and the shared formal design |
| realm, Node module, web subsystem, diagnostics and test capsules | different lifetimes and reset policies |
| request parser and parsed request head | parsing state versus completed semantic result |

Large resource records such as `JsSocket`, `JsTlsSocket`, and `JsSpawnProcess` are not automatically split because they have many fields. Split them only where tracing shows an independent lifecycle—for example a reusable IO resource core, TLS layer, event-emitter state, or pending operation—not to satisfy a size target cosmetically.

### 14.1 Structural ratchets

**`JsMirTranspiler` — ratchet MET 2026-09-08 at 664 B.** §9.3 took it from
30,840 to 2,720 B; §9.2's first split takes it to **664 B**, well under 2,048.
`JsMirFunctionEmitter` (1,560 B) now holds the per-function lowering state:
`MirEmitter em`, `MirValue last_call_result`, and the two 32-entry name caches
with their counts and function-item guards. Those caches are what identified the
boundary — each invalidates itself against `em.func_item`, which is the
definition of per-function state sitting in a compilation-unit record. 319
accesses were rewritten across eleven files.

⚠ The member is named `func_em`, not `fn`: the call macros in
`js_mir_internal.hpp` already bind a parameter called `fn`, so `(mt)->fn->em`
expanded the macro argument into the member path and produced nonsense that
still parsed at some sites.

**Honest note on what this buys.** `JsMirTranspiler` is one instance per
compilation unit, so the byte count was never memory pressure — the value is
that the per-function boundary now has a name and one record to reset, instead
of a dozen fields reset by scattered assignments. Lowering is sequential, so the
emitter is allocated once and reused rather than reallocated per function; §14.1
would object to that shape for a record every realm carries, but here the
coordinator genuinely no longer contains state whose lifetime is a function
body. The remaining four records §9.2 names — control flow, generator lowering,
eval lowering — are still inline; they are small, and splitting them further
buys structure rather than either bytes or a ratchet.

**`JsRuntimeState` — 27,064 → 9,120 B this session; ratchet ≤ 1,024 still
misses.** Two things came out:

- **`JsDomPlatformState` (5,680 B) became a lazy context capsule.** Local and
  session storage and media-query state are DOM-only, so a plain JS realm never
  materialises them. Read paths use `context_capsule`, not
  `context_capsule_ensure` — a batch reset of a realm that never touched storage
  must not allocate the capsule just to clear it.
- **The native wrapper cache (12,288 B) grows instead of being two fixed 512-entry
  tables.** This was 57 % of the record. It also stopped being a cache in
  ordinary use: a bare realm already reaches ~5,000 reachable functions, so the
  512 slots saturated and every later wrapper simply missed. Function identity
  is unaffected either way — verified against Node before and after — because a
  compiled function's Item is stored once at its binding rather than rebuilt per
  reference, so this was a size and hit-rate problem, not a correctness one. The
  cached wrappers are pool-backed and carry no registered GC root, so the arrays
  may move.

**What reaching ≤ 1,024 now requires.** The remainder is almost entirely the ~38
records still embedded by value. The largest is `JsEvalState` (4,304 B), of
which `JsEvalBridgeState` is 2,920 B — four `bool[512]` flag arrays parallel to
`RootVector`s plus three `int` frame-mark arrays, exactly the "parallel fixed
arrays encode records by position" shape §2 flagged. Those caps are *diagnosed*
(`js-eval-env: binding stack overflow`), unlike the silent ones fixed elsewhere,
so converting them is a size change rather than a correctness fix. Beyond that,
closing the ratchet is §4's capsule-directory conversion applied to the whole
set, and the honest test stays the one above: a record every realm uses is not
served by a pointer, only the ones a plain JS realm never touches become
capsules.

## 15. Expected result

After P9:

- An empty LambdaJS context allocates a small directory and only the capsules actually used.
- Every rooted native collection has one stable-address mechanism; object-specific edges live on their GC owner.
- Generators, async frames, observers, XHR operations and native resources have object/resource identity rather than recyclable context indexes.
- Protocol and configuration records allocate in proportion to input, while explicit safety limits remain checked policy.
- A JS function value contains value state; immutable callable/code facts are shared.
- Compiler declarations, analysis, plans and emission state have separate ID-keyed authorities.
- Full reset constructs a fresh realm; checkpoint reset is a typed transaction; adding a subsystem does not require editing unrelated root/reset lists.
- Catalog IDs and event queues remain semantically distinct even though their construction and storage mechanisms are consolidated.

That is the practical meaning of “one concept/mechanism, one struct” for LambdaJS: one authority and lifecycle per idea, with reuse through references and shared infrastructure instead of mega-struct embedding, parallel arrays, and hard-cap registries.
