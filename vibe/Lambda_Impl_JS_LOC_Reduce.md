# LambdaJS C++ LOC Reduction (JLR)

**Goal:** reduce hand-written C/C++ under `lambda/js/` by ≥3,000 lines via
(1) retiring legacy code, (2) reusing Lambda-runtime code instead of JS-local
re-implementations, (3) unifying near-identical data structures and code flows.
Blank lines, comments and formatting are **not** a lever — only real code.

Authority: cite `D#` from `doc/Lambda_Formal_Design.md` first (rule 17); this
file is the working ledger.

### Ruled out by measurement (do not re-investigate)

- **A dead subsystem.** `js_bt_regex.cpp` is the live backtracking fallback RE2
  structurally cannot serve; `js_interp.cpp` is the AST backend that
  `JS_EXECUTION_BACKEND=ast` gates in `test_js_script_gtest`; no tree-sitter JS
  path survives. Nothing here is retirable.
- **Per-type builtin families.** `js_buffer.cpp`'s 88 `read*`/`write*` entry
  points are already generated by `JS_BUFFER_READ_FIXED`/`_FLOAT`/`_VARIABLE`/
  `_BIGINT` macros. Typed arrays likewise.
- **`strcmp` dispatch chains.** 865 sites tree-wide; the catalog work already
  took that vein.
- **Reusing Lambda's JSON/printer for JS.** `JSON.stringify`/`util.inspect`
  output formats are spec/Node-observable and do not match Lambda's.

## Landed detail (batch 1)

- **JLR1** `js_c_take_arity(sink, reduction, lo, hi, &nodes)` folds the
  `child_count` range check into the take. Compound guards of the shape
  `if (child_count != 2 || !js_c_take_values(...)) return false;` were left
  alone **on purpose**: they do *not* set `sink->unsupported` on an arity
  mismatch, and collapsing them would change which failure the caller sees.
- **JLR3** each `*RealmItems` record is exactly one `Item*` per realm slot in
  slot order, so the record is the lookup's output array. Field order was
  verified against slot order for all five records before the change, and a
  `static_assert` on `sizeof` now pins the count at every use site. All 20
  callers already check the bool result, so the partial-fill-on-failure that
  this introduces is unobservable.
- **JLR4a** `str_hex_val` is `static inline` in `lib/str.h`; `str_is_hex` now
  derives from it. `js_bt_regex.cpp` needed an explicit `lib/str.h` include.
- **JLR4b** the five moved bodies were proved character-identical to the core
  file's (modulo the rename) before the JS copies were deleted, so the golden
  `--emit-js-ast-dump` output cannot move. The two kind-name tables were
  deliberately **not** merged: their spellings (`JS_AST_NODE_*` vs
  `AST_NODE_*`) are the dump's observable contract, and an X-macro rewrite of a
  one-entry-per-line table saves nothing without packing lines, which the task
  forbids.

## Landed detail (batch 2)

- **JLR6** two finish helpers, because the two families build different string
  kinds: `assert_take_string` goes through `assert_make_string_n`
  (`heap_create_name`, interned), `js_strbuf_take_item` through `heap_strcpy`
  (GC string). The 3 `heap_create_name` + StrBuf sites in `js_runtime.cpp` were
  left alone — a third helper costs more than the 6 lines it would save.
- **JLR7** `JS_ARRAY_FOREACH(name, array)` lowers to
  `for (...) if (Item name = js_elements_get_int(...); true)`. The C++17
  init-`if` form is what makes `break`, `continue` and `return` all behave as
  written — the tempting triple-`for` alternative silently swallows `break`.
  Verified with a standalone probe before applying. Only the **63 of 75** sites
  whose body touches neither the index nor the length were converted; the other
  12 keep an explicit loop. One converted site (`js_runtime.cpp` vm.Module
  linking) used the length *after* the loop and was reverted — the body scan
  did not see that.
- **JLR8/JLR9** `js_alloc_env` already returns zeroed memory
  (`heap_calloc_closure_env`), so the alloc-and-fill collapse has no
  half-built-env exposure. **One site was deliberately left expanded**
  (`js_net.cpp:3344`): its third value is `make_string_item(nr->host)`, which
  allocates. As an argument it would sit in a bare temporary across the env
  allocation; stored into the slot it is traced immediately. All other 100
  sites pass non-allocating expressions, so C++'s unspecified argument
  evaluation order cannot matter.

## Landed detail (batch 3)

- **JLR10** the 44 `#define JS_*_BODY` macros in `js_runtime.cpp` all respelled
  the same five-parameter native signature. Now three generics own it and the
  rest either alias one (`#define JS_RUNTIME_THIS_BODY JS_INTRINSIC_BODY`) or
  wrap one. **Use sites are untouched** — the specialized names still exist,
  which is the whole point: they keep the ~500 invocation lines short.
  - The eight arg-binding macros were three different spellings of the same
    thing; they now all bind through `js_intrinsic_arg`, which is the
    **null-safe** form. `JS_GLOBAL_UNARY_BODY` and friends used a bare
    `argc > 0 ? args[0]`, so this only tightens behaviour for a NULL `args`.
  - Two generics (`_ARG1_`/`_ARG2_`) rather than one that always binds `arg1`:
    binding an unused second argument would cost work in hot global builtins.
  - `JS_DEFINE_ERROR_CTOR_CALL_BODY` pastes its function name
    (`js_intrinsic_ctor_##token##_call_body`), so it needs the pasted spelling
    passed through, not the macro parameter. The first mechanical pass got this
    wrong and the **linker** caught it — the compiler did not.
- **JLR12** the primitive landed in `lambda/runtime/root_vector.{h,cpp}`, not in
  a JS header: rows and their RootVector are one logical table, and freeing the
  rows without clearing the roots leaves the GC tracing freed payloads. That
  invariant belongs with `RootVector`.

## Landed detail (batch 4)

- **JLR13** is the one real "reuse Lambda code" find left: `lambda/core` already
  had `bigint_from_uint64`, and it is a **better** implementation — it calls
  `mpd_set_u64` directly, where all three JS copies detoured through
  `snprintf` + `bigint_from_string` for values above `INT64_MAX`. So this
  removed 18 lines *and* a decimal round-trip from Buffer, DataView and fs.
  (The first attempt added a fourth copy to `lambda-decimal.cpp` before the
  redefinition error revealed the existing one — check the core before adding
  to it.)
- **`js_c_wtf8_encode` vs `lib/utf.c`'s `utf8_encode` looks like a duplicate and
  is not.** They differ in exactly one line: `utf8_encode` rejects surrogates,
  `js_c_wtf8_encode` encodes them, which is the whole difference between UTF-8
  and WTF-8 and the reason JS can hold a lone surrogate. Do not "unify" these.

## Budget, re-measured after batch 3 — the 3,000 target is not reachable this way

The batch-1 estimate of ~3,300 was too optimistic: it read lizard's *gross*
duplicate lines, which double-counts overlapping windows and ignores the helper
each extraction costs. A proper greedy, non-overlapping census of exact repeated
runs (keep one copy, replace each other with one call line) gives:

| tier | gross saving | practical? |
|------|--------------|------------|
| W≥5 | 124 | yes |
| W=4 | 390 | yes |
| W=3 | 772 | mostly |
| W=2 | 1,438 | **no** — 719 groups each saving 1 line, every one needing a 4–6 line helper |
| **total** | **2,724** | **~1,286 addressable** |

Those 1,286 gross lines sit in **220 groups**; the largest now saves 26 lines
and the median saves 5. After helper overhead the realistic net is **~200–350**.

Adding everything still on the table:

| source | realistic net |
|--------|---------------|
| remaining exact-repeat groups (220) | 200–350 |
| remaining whole-function clone groups (55, 553 gross) | ~350 |
| `js_ast.hpp` alias shim (JLR5) | ~180 |
| JLRO1 dead `(void)param;` lines | 167 |
| **remaining total** | **~900–1,050** |

With **−817 already landed**, the ceiling for behaviour-preserving dedup is
roughly **1,700–1,900 lines — not 3,000**. Reaching 3,000 needs a different
kind of change (deleting a capability, or moving the builtin catalog to
build-time generation), which is a product decision, not a refactor.

### FINAL measurement (after batch 4) — the estimate above was still too high

Both earlier estimates counted *gross* duplicate lines. Charging each extraction
its helper (`W + 3` lines: signature, body, close, blank) and assuming every call
site collapses to one line, the greedy non-overlapping census over all
`lambda/js/*.cpp` gives:

- 2,698 repeated groups, **5,394 gross** lines
- of these, **only 27 groups have a positive net** — and they total **86 lines**
  (largest 12, then 8, 6, 6, 6, 5 …)

The whole-function clone census tells the same story: 507 gross across 55
groups, but 2-copy groups do not survive parameterization (the
`socket_configure_abort_signal` / `js_http_client_configure_abort_signal` pair
is 23 identical-looking lines that needs ~20 lines of callbacks and out-params
to merge — a net saving of about 6). Only 3+-copy groups pay: **~55 net**.

The cross-boundary hunt (`lambda/js` vs `lambda/core`, `lambda/runtime`, `lib`)
is likewise exhausted: 19 candidate pairs, of which exactly two were real (the
AST dumper in batch 1, `bigint_from_uint64` here) and the rest are either
structural coincidence or deliberate variants like WTF-8.

| source | realistic **net** |
|--------|-------------------|
| remaining exact-repeat groups | **86** |
| remaining function clones (3+ copies) | **~55** |
| `js_ast.hpp` alias shim (JLR5) | ~180 |
| JLRO1 dead `(void)param;` lines | 167 |
| **remaining total** | **~320, or ~490 with JLRO1** |

**Final: −846 landed + ~320–490 remaining ⇒ a ceiling near 1,200–1,350 lines,
not 3,000.** Everything past that changes behaviour, deletes a capability, or
moves code to build-time generation.

## Landed detail (batch 5) — user chose "take JLRO1 + JLR5"

- **JLRO1** re-measured at 164 (not 167) because JLR10 had already absorbed
  three of them into the generic body macros. Build warnings unchanged.
- **JLR5** covered the **constant** half of the shim: 108 `static const`
  aliases, 1,795 references. The rename is semantics-preserving by
  construction — every alias was already *defined as* the core constant.
  - Exactly one many-to-one mapping exists: `JS_AST_NODE_WHILE_STATEMENT`,
    `_FOR_STATEMENT` and `_DO_WHILE_STATEMENT` are all `AST_NODE_LOOP`. They
    were already the same value, so any `switch` holding two of them would have
    been a duplicate-case error *before* this change too — and the build
    confirms none exists. The rename only makes the existing conflation visible.
  - `js_ast.hpp` referenced one of its own aliases (`js_ast_identifier_named`),
    which the first pass missed by excluding the file from the rename.
  - The 8 JS-only node kinds (`(JsAstNodeType)1002`…`1027`) are **not** aliases
    and stay. Folding them into the core `AstNodeType` enum is a separate change.

### The typedef half of the shim was deliberately NOT taken

`js_ast.hpp` also holds 43 `typedef Ast* Js*Node;` aliases, worth 43 lines
against **~4,000** references. Beyond the ratio, 8 of them are not redundant
spellings at all — several distinct JS concepts share one core struct, and the
JS name is the only thing recording which:

| core struct | JS spellings that would collapse into it |
|-------------|------------------------------------------|
| `AstArrayNode` | `JsArrayNode`, `JsArrayPatternNode`, `JsSequenceNode` |
| `AstAssignNode` | `JsAssignmentNode`, `JsAssignmentPatternNode` |
| `AstMapNode` | `JsObjectNode`, `JsObjectPatternNode` |
| `AstIfNode` | `JsConditionalNode` |

Collapsing those makes `AstArrayNode* x` ambiguous between an array literal, an
array pattern and a sequence expression. Only the unused `JsLiteralType` was
removed. Retiring the rest is available but needs a separate decision.

## Levers found but NOT taken (need a user call)

- ~~JLRO1~~ **TAKEN in batch 5** (164 lines). Original note: 167 dead `(void)param;` suppression lines. `-Wno-unused-parameter`
  sits in the **global** `flags` array of `build_lambda_config.json`, so every
  config on every platform already disables the warning these lines suppress:
  they are no-ops. Removing them is worth 167 LOC (81 in `js_runtime.cpp`
  alone, mostly the uniform 5-parameter `js_intrinsic_*_body` ABI). **Not
  taken** because it is none of the three requested means — it neither retires
  a legacy path, reuses Lambda code, nor unifies a structure — and it costs the
  in-source signal that a parameter is deliberately unused. Say the word and it
  is a one-command change (`temp/jlr5_voidparams.py --apply`).

## Budget reality (measured, 2026-09-11)

The honest ceiling for *behaviour-preserving* reduction, from the censuses
above: ~2,500 net from block clones (4,766 gross less helper overhead) + ~400
from function clones + ~180 from the AST shim + ~250 cross-boundary ≈ **3,300**.
So the 3,000 target is reachable but sits near the top of what exists, and it
arrives as ~80–100 separate extractions of 20–80 lines each, not as a few large
wins. There is no remaining single change worth more than ~200 lines that does
not delete a feature.
