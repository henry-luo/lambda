# Lambda Impl: Runtime Struct and Type Clean-Up

- **Date:** 2026-08-18
- **Status:** PROPOSAL — P1.1 implemented 2026-09-01; remaining stages pending
- **Scope:** native Lambda data/runtime (`lambda-data` + `lmd-rt`), with shared `lib` and C ABI structures where they define the runtime boundary. LambdaJS and Radiant are consumers and compatibility gates, not primary clean-up targets.
- **Principle:** one concept or mechanism has one authoritative struct. Semantic distinctions may share physical storage; unrelated ownership, cache, compiler-fact, and guest-language concerns must not accumulate in the same struct.
- **Formal authority:** D1.2 (one `Item` currency), D1.3 (one runtime; guests reuse contracts, not accidents), D1.4v3 (explicit completion), D1.8 (decisions are carried), D2.1 (Item/container model), D2.4.1 (four facts/four authorities), D2.6.1 (three array forms and one storage-descriptor resolver), D3.1.1v2 (one `Type*` graph), D3.4.1–D3.4.7 (shape ABI), D5.2.1v3 (companion-lane returns), D5.4.1–D5.4.2 (one `EvalContext`), D6.2.1–D6.2.2v2 (function values and dispatch), D6.4.1 (boxed sys-function boundary), D7.1.5 (Mark API ownership), D7.4.5 (virtual carriers), D8.2.2/D8.2.4/D8.2.5 (unified AST, IDs, fact tables and pass manager). Semantic guardrails: S5.3.1 (one sequence family), S5.4.2 (objects remain nominally distinct), S5.5.1 (function identity).
- **Census artifacts:** `vibe/meta/ds/struct_census.csv` and `vibe/meta/ds/struct_census.json`, generated by `utils/struct_census.py`.
- **ID series:** `SCU1`–`SCU6` are the local proposal ledger. Implementation stages are `P0`–`P9`.

## 0. Outcome

The runtime should converge on five authoritative chains:

```text
Type* -> RecordType -> Shape -> ShapeField[] -> StorageDesc
Item  -> ContainerHeader -> SequenceStorage | RecordStorage

FunctionValue -> FunctionCode -> FnAbiContract
Runtime -> EvalContext -> lazy subsystem capsules
CompilationUnit -> dense IDs -> typed fact tables
SourceSpan -> SourceIndex
```

The census shows that the main problem is not the absolute number of declarations. It is four kinds of structural duplication:

1. **The same decision is represented repeatedly.** Return shape, scalar mode, error lane and call transport are mirrored across AST analysis, MIR plans, call metadata, function flags and system-function metadata.
2. **One struct owns several concepts.** `TypeMap`, `Runtime`, `Function`, `VarEntry`, `MirTranspiler`, `Script` and `Transpiler` have accumulated unrelated state.
3. **One physical layout is declared repeatedly.** Map/Object/Element record storage and the C/C++ `Item`/container declarations are parallel representations of the same ABI.
4. **Capacity is embedded instead of owned dynamically.** Source line indexes, markup link definitions, YAML anchors, shape-builder fields and per-`TypeMap` lookup indexes make ordinary instances pay for maximum documents.

The target is not a universal `Type`, universal `Container`, or universal compiler-context mega-struct. The target is one source of truth for each concept, referenced by all consumers.

## 1. Census method and scope

The census was run with:

```bash
python3 utils/struct_census.py --top 35
```

The run parsed 529 translation units with no reported hard parse errors and found:

| Scope | Definitions |
|---|---:|
| all configured modules | 2,643 |
| `lambda-data` | 560 |
| `lmd-rt` | 547 |
| native Lambda slice | **1,107** |

The native slice deliberately excludes the 485 `js-rt` and 770 Radiant definitions except where those systems have placed state in shared Lambda records. This keeps the proposal centered on the substrate rather than treating guest/runtime-specific data models as Lambda concepts (D1.3).

Important census limitations:

- A definition's byte size is not its total live-memory footprint or allocation count.
- Function-local structs are absent because the census skips function bodies.
- Template layouts can be absent until instantiated.
- The result reflects the macOS debug preprocessor configuration.
- Header definitions deduplicated by clang USR can hide source-level C/C++ conditional duplication. This matters for `Item`, `Range`, `List`, `Map`, `Object` and `Element`, whose physical layouts are separately spelled in `lambda.h` and `lambda.hpp`.

The census is therefore evidence for investigation, not an automatic deletion list.

## 3. Governing rules

### SCU1 — One struct means one authority, not one spelling

A struct is authoritative when it is the only owner of a fact and every consumer receives or references it. A typedef, pointer, immutable view or typed accessor may expose the same authority without creating a second mechanism.

### SCU2 — Semantic type and physical representation stay separate

D2.4.1 explicitly assigns separate authorities to the semantic `Type*`, lowering representation plan, emitted `MirValue`, and MIR physical register type. Clean-up must remove mirrored facts, not collapse those four layers.

For example, `ShapeField.contract` owns the full semantic `Type*`, while `ShapeField.storage` owns the derived physical `StorageDesc`. The descriptor does not become a second semantic contract.

### SCU3 — Derived state is referenced or side-tabled

Lookup tables, transition caches, prototype caches, emitted register locations and pass results are derived state. They must not enlarge the canonical semantic record unless every instance requires them and the hot-path benefit is measured.

### SCU4 — Shared storage does not erase language meaning

Map and Object may use one `RecordStorage`, but S5.4.2 requires distinct semantic families. Range, List, boxed Array, native Array and ArrayNum may share sequence operations, but D2.6.1 requires the three physical array forms. Representation consolidation must preserve those rulings.

### SCU5 — No fixed-capacity document limits in parser objects

Parser working sets grow from their actual source. No parser instance embeds storage sized for the maximum number of lines, links, anchors or fields. Exhaustion reports an allocation/resource error rather than silently truncating a valid document (D1.9).

### SCU6 — ABI records are declared once

Every C-visible layout has one canonical POD declaration and one set of offset/size assertions. C++ behavior is supplied by free functions or non-owning views, never by a second structural definition.

## 4. Type and shape consolidation

### 4.1 Canonical type-node header

D3.1.1v2 says a first-class type value is one `Type*` graph node under `LMD_TYPE_TYPE`, discriminated by `Type.kind`. The current graph is transitional: simple type descriptors often carry their value-domain `TypeId` in `Type.type_id`, while `TypeType` wraps a second `Type*` to expose a type value.

Target conceptual layout:

```c
typedef struct Type {
    TypeId type_id;       // LMD_TYPE_TYPE for a first-class type node
    TypeKind kind;
    TypeId value_domain;  // int, string, map, object, ...
    uint16_t flags;
} Type;
```

Exact packing is an implementation decision, but the concepts are fixed:

- `type_id` identifies the graph node as a type value.
- `value_domain` identifies the admitted value family.
- `kind` selects the graph-node payload.
- `Type*` remains the semantic-contract authority.

Consequences:

- Delete `TypeType`.
- Delete the parallel `LIT_TYPE_*` wrapper singleton family.
- Reduce `TypeInfo` to one canonical `Type*`, its display name and the canonical storage description/reference.
- Replace call-site unwrapping with direct `Type*` use.
- Add a temporary checked compatibility accessor during migration; remove it when no wrapper remains.

### 4.2 One scalar-literal type node

The current scalar-literal family contains `TypeFloat`, `TypeComplex`, `TypeInt64`, `TypeNumSized`, `TypeUint64`, `TypeDateTime`, `TypeDecimal`, `TypeString`/`TypeSymbol` and `TypeBinaryConst`, all extending `TypeConst`.

Replace these with one concept:

```c
typedef struct TypeLiteral {
    Type base;
    int32_t const_index;
    Item value;
} TypeLiteral;
```

The `Item` is a canonical literal value. Pointer-backed literal payloads must have stable ownership in the type/Input arena; dynamic datetime and wide-scalar ownership continues to obey D2.2.3. No literal node may borrow a temporary number home.

This removes type-specific record proliferation without introducing a maximum-sized literal union.

### 4.3 Canonical storage descriptor

There is one physical-storage decision used by MIR lanes, packed map fields, native arrays and guest boundaries (D2.6.1). Define one compact `StorageDesc`:

```c
typedef struct StorageDesc {
    uint8_t kind;
    uint8_t width;
    uint8_t nullable;
    uint8_t flags;
    TypeId value_domain;
} StorageDesc;
```

The precise packing may change, but it must not contain a second owning `Type*`. The full semantic contract lives beside it. One resolver:

```text
storage_desc_for(Type*) -> StorageDesc
```

is used by shape construction, packed-field reads/writes, array planning, MIR lowering and guest adapters. Parallel switches over `TypeId`, `LaneStorageKind`, `ArrayNumElemType` or MIR register type are retired or reduced to explicit boundary conversions.

### 4.4 Immutable Shape and ShapeField

`ShapeEntry` currently combines runtime layout with namespace/default-expression data and JS descriptor state. `TypeMap` then owns the chain, tail, lookup indexes, transitions, trust certificates and JS caches.

Target concepts:

```c
typedef struct ShapeField {
    NameId name_id;
    uint32_t name_hash;       // routing only, never identity
    Type* contract;
    StorageDesc storage;
    uint32_t byte_offset;
    uint8_t key_kind;
    uint8_t descriptor_flags;
} ShapeField;

typedef struct Shape {
    uint64_t hash;
    uint32_t field_count;
    uint32_t byte_size;
    uint32_t flags;
    ShapeField fields[];
} Shape;
```

Compile-time declaration-only data moves to `RecordFieldDecl` keyed by field/binding ID:

- namespace target
- default expression
- source span
- declared annotation provenance

Runtime-only caches move to side structures:

- `ShapeLookup` for optional hash/slot indexes
- `ShapeTransitions` for mutable record evolution
- JS prototype/cache tables in `JsRuntimeState`, keyed by `Shape*` or runtime record family

The immutable `const JsClassMeta*` refinement allowed by D3.4.7 may remain on a thin runtime record type/family descriptor. Mutable `js_proto_entry_cache` may not remain on the core immutable shape.

### 4.5 RecordType becomes a thin semantic node

`TypeMap` should become a small record contract rather than the shape mechanism itself:

```c
typedef struct RecordType {
    Type base;
    Shape* shape;
    const RecordSemantics* semantics;
    uint32_t type_index;
    uint32_t flags;
} RecordType;
```

Map, Element and Object retain thin semantic refinements where necessary:

- Map: structural record semantics.
- Element: tag/namespace/content contract plus attribute `Shape*`.
- Object: nominal identity, base object, method table and constraint.

They do not inherit 376 bytes of lookup and cache machinery. Sharing a `Shape` never makes Map and Object interchangeable (S5.4.2).

### 4.6 Shape-pool simplification

Today `ShapeSignature`, `CachedShape`, `ShapePoolEntry`, a linked `ShapeEntry` chain and per-`TypeMap` indexes all describe aspects of one interned shape.

The target pool maps a structural key directly to immutable `Shape*`. The `Shape` owns count, byte size, hash and fields; there is no separate `CachedShape.last` or reference-count field when the arena/pool already owns lifetime.

`ShapeBuilder` becomes a small dynamic builder:

```c
typedef struct ShapeBuilder {
    ShapePool* pool;
    ArrayList* fields;   // ShapeFieldDraft
    RecordKind kind;
    NameId element_name;
} ShapeBuilder;
```

It carries full `Type*` contracts and has no 64-field hard limit.

### 4.7 Required formal revision

This proposal does not itself change a formal ruling. Before the contiguous `Shape` representation lands:

1. Revise D3.4.1 in place to v2: replace the normative `ShapeEntry` chain with the immutable `Shape`/`ShapeField` ABI.
2. Revise D3.4.2 in place to v2: shape identity must include the normalized full field contract/storage identity, not only `TypeId`, because D3.4.6 requires full-contract-derived storage.
3. Bump the formal-design document semver.
4. Update the relevant shape working-design ledger in the same change.

Until that revision lands, the linked chain remains normative.

## 5. Item and container consolidation

### 5.1 One Item representation

D1.2 and D2.1.1 require one 64-bit `Item` value currency. C currently uses an integer `Item`; C++ defines an 8-byte union/class view and a second `ConstItem` union.

Long-term target:

```c
typedef uint64_t Item;
```

in both C and C++, with:

- canonical construction and extraction helpers
- typed pointer accessors such as `it2map`
- optional non-owning C++ view classes containing an `Item`, never redefining its ABI
- no `ConstItem` reinterpretation/cast path

This is a high-churn ABI migration and intentionally comes after the type/shape cleanup has reduced the number of consumers.

### 5.2 One record-storage body

Map and Object have the same physical fields; Element repeats them. Define one storage body:

```c
typedef struct RecordStorage {
    void* type;
    void* data;
    int32_t capacity;
} RecordStorage;
```

and one sequence body:

```c
typedef struct SequenceStorage {
    Item* items;
    int64_t length;
    int64_t extra;
    int64_t capacity;
} SequenceStorage;
```

Then:

- Map/Object contain `ContainerHeader + RecordStorage`.
- List/boxed Array contain `ContainerHeader + SequenceStorage`.
- Element contains `ContainerHeader + SequenceStorage + RecordStorage`.
- ArrayNum retains its specialized numeric storage required by D2.6.1.

The emitted ABI continues to use asserted offsets. Accessors replace direct spelling differences during migration.

### 5.3 Container header audit

The eight-byte `Container` header currently mixes universal lifecycle/COW state with sequence views, native-array state, map kind, JS elements state and constructor masks.

Do not enlarge or reshuffle it speculatively. Preserve the one-byte COW fast path required by D4.4.1. Audit every bit into one of three categories:

1. universal container state — remains in `ContainerHeader`
2. family-specific hot state — moves only if measurements show no regression
3. guest/runtime cache state — moves to an explicit sidecar

Any header change requires size/offset assertions and release-build benchmarks (`make release`); debug performance numbers are invalid.

## 6. Return and callable consolidation

### 6.1 Delete the Ret* type family

The typed `RetBool`, `RetInt56`, `RetInt64`, `RetFloat`, `RetString`, `RetSymbol`, `RetMap`, `RetList`, `RetElmt`, `RetObj`, `RetArray`, `RetRange` and `RetPath` records are one abandoned mechanism. They have constructors registered for JIT visibility but no native functions actually return those typed aggregates.

Delete them and their constructors/registry entries.

**P1.1 implemented (2026-09-01).** The thirteen typed aggregate records,
constructors, registry exports, and the test that existed solely for that
abandoned API are deleted. A whole-tree use scan found no native function that
returned a typed aggregate. `RetItem` and `C_RET_RETITEM` remain active pending
the distinct P1.2 companion-lane migration required by D5.2.1v3.

Migrate active `RetItem` functions to the formal completion model:

- public/system-function boundary: one boxed `Item` (D6.4.1)
- failure: ERROR-tagged `Item` with rich `LambdaError` payload (D1.4v3)
- generated proven-native entry: declared companion error lane (D5.2.1v3)

No C aggregate return is used as an alternative ABI. Once all active users migrate, delete `RetItem`, `C_RET_RETITEM`, its interpreter dispatch branch and the MIR wrapper/trampoline layer created to work around aggregate ABI incompatibility.

### 6.2 One function ABI contract

Return and entry decisions are currently mirrored in `FnReturnAnalysis`, `MirScalarReturnMode`, `FunctionReturnLaneKind`, `MirFunctionPlan`, `JitCallMetadata`, `Function` flags and `SysFuncInfo`.

Define one immutable planning product:

```c
typedef struct FnAbiContract {
    FnEntryKind entry_kind;
    FnReturnShape return_shape;
    FnCompanionTransport companion;
    FnReturnLane normal;
    FnReturnLane error;
    uint32_t flags;
} FnAbiContract;
```

One `FnEffects` record separately owns GC, re-entry, exception, number-stack, suspension and argument-capture effects. ABI and effects are not combined merely because call sites consume both.

Delete or derive:

- `MirScalarReturnMode`
- `FunctionReturnLaneKind`
- `FnErrorLane` where `FnReturnShape` already decides it
- mirrored public-return-shape flag bits
- call-site recomputation from local `TypeId` or MIR register type

`MirFunctionPlan`, `JitCallMetadata`, function code and system-function descriptors reference the same `FnAbiContract`.

### 6.3 Split function value from function code

Today's `Function` mixes immutable code/signature/identity metadata with per-value closure data and a context pointer.

Target:

```c
typedef struct FunctionCode {
    TypeFunc* signature;
    FnAbiContract* abi;
    FnEffects* effects;
    fn_ptr checked_entry;
    fn_ptr boxed_entry;
    const char* name;
    FunctionSite site;
    uint32_t flags;
} FunctionCode;

typedef struct FunctionValue {
    ContainerHeader header;
    FunctionCode* code;
    void* closure_env;
    uint16_t closure_field_count;
} FunctionValue;
```

The exact ABI-sensitive header packing remains asserted. `FunctionSite` stores the static `(module, node)` identity required by D6.2.1 and S5.5.1. The closure environment remains precisely traced. Per-function `runtime_context` disappears once D5.4.1's canonical TLS context is universal; it must not be removed earlier.

`TypeMethod` reduces to method name plus `FunctionCode*` and linkage. `SysFuncInfo` references or embeds the same callable descriptor and adds only system-function-specific overload/result-derivation rules.

## 7. Runtime ownership consolidation

### 7.1 Separate ABI prefix from isolate ownership

D5.4.2 freezes the JIT-visible `Context` prefix, while D5.4.1 gives `EvalContext` canonical isolate ownership. Make that separation explicit:

```c
typedef struct EvalAbiContext {
    // frozen generated-code fields, byte-for-byte compatible with Context
} EvalAbiContext;

typedef struct EvalContext {
    EvalAbiContext abi;       // first field; checked offset 0
    Heap* heap;
    NamePool* name_pool;
    TypeRegistry* types;
    LambdaScheduler* scheduler;
    EvalCapsules capsules;
    // diagnostics and active-module state
} EvalContext;
```

Composition replaces C++ inheritance. Generated code continues to receive the frozen prefix. Native helpers resolve the containing canonical `EvalContext` through the sanctioned TLS root.

### 7.2 Runtime is a controller, not a second owner

`Runtime` keeps:

- loaded compilation units/modules
- module registry and cache policy
- compile/configuration flags
- one `EvalContext*`
- shell/document integration references appropriate to its layer

`EvalContext` alone owns:

- heap
- name pool
- type registry
- scheduler
- module-state slabs
- runtime subsystem capsules

Remove the mirrored `Runtime.heap`, `Runtime.name_pool`, `Runtime.type_list`, `Runtime.scheduler` and transitional `js_bootstrap_context`. Runner setup selects/configures the canonical context but never copies ownership back and forth.

### 7.3 One input-allocation context

Input parsing has a different ownership boundary from evaluation and correctly uses a minimal `InputAllocationContext`. Retire the legacy `Context* input_context` dependency from collection construction and keep one input-allocation TLS selector where an explicit parameter is not yet practical.

The evaluation TLS remains the single `EvalContext` root required by D5.4.1. Input allocation is a scoped IO construction policy, not a second evaluation identity.

### 7.4 Mark APIs share storage authority, not capability

`MarkBuilder` and `MarkEditor` repeat cached `Input`, Pool, Arena, NamePool, ShapePool and type-list pointers. Introduce one non-owning `InputStorage`/`InputContextView` obtained from `Input*` and referenced by both.

Do not merge `MarkReader`, `MarkBuilder` and `MarkEditor`. D7.1.5 deliberately separates core reading from IO-owned building/editing, and their capability/lifecycle models are distinct.

## 8. Source and parser-state consolidation

### 8.1 Canonical SourceSpan

Replace both `SourceLocation` definitions and retained `TSNode` locations with:

```c
typedef uint32_t SourceId;

typedef struct SourceSpan {
    SourceId source_id;
    uint64_t start_offset;
    uint64_t end_offset;
} SourceSpan;
```

One `SourceIndex` per source owns its dynamic line-start table and source metadata. File, line, column and context text are derived through it. A diagnostic or AST node stores a `SourceSpan`, not source pointers plus already-derived line/column copies.

This gives parser errors, runtime errors, stack frames and compiler diagnostics one location mechanism while allowing each error type to remain a distinct concept.

### 8.2 Dynamic parser working sets

Replace:

- `SourceTracker.line_starts_[100000]` with a lazily built `ArrayList`/arena array
- `MarkupParser.link_defs_[256]` with a dynamic collection
- inline `LinkDefinition.label[256]`, `url[1024]`, `title[512]` with interned strings or source spans
- `YamlParser.anchors[256]` and `AnchorEntry.name[256]` with a dynamic name-to-Item table

No silent `if (count >= 256) return` remains. Allocation failure becomes an explicit parser/resource error.

`InputContext` holds a pointer/reference to `SourceIndex`; it does not embed the index. The fixed footprint of `MarkupParser` should become independent of document line/link counts, with a target below 16 KiB before dynamic allocations.

## 9. Compiler-state consolidation

### 9.1 Binding identity plus fact tables

D8.2.4 requires dense stable binding IDs; D8.2.5 requires optimization facts in ID-keyed side tables. Replace `NameEntry`/`VarEntry` fact accumulation with:

```text
BindingId -> BindingDecl
          -> BindingTypeFacts
          -> BindingStoragePlan
          -> MirBindingLocation
          -> OwnershipFacts
          -> guest-specific facts
```

`BindingDecl` owns only source identity and declared semantics: name, scope, declaration node, mutability, source contract and import origin. Interpreter slots, MIR registers/root homes, COW analysis, typed-array caches and JavaScript-only state live in their producing pass's table.

This may introduce several small fact structs while deleting the 46-field cross-language `VarEntry`. That is a successful application of the principle: each fact family has one owner, and facts are allocated only for passes that produce them.

### 9.2 CompilationUnit replaces inheritance layering

`Script : Input` and `Transpiler : Script` conflate document storage, source/CST, AST, module identity, compiler diagnostics, interpreter plans, MIR state and active lowering context.

Target composition:

```text
InputDocument     — parsed Mark/input data and its allocators
CompilationUnit   — source, CST, AST, dense index, constants, imports, module identity
CompilerSession   — configuration, diagnostics, pass manager
MirModuleEmitter  — module-level MIR state
MirFunctionEmitter — one function's lowering/frame state
Runtime           — loaded-unit lifecycle and execution controller
```

`CompilationUnit` owns the language profile as required by D8.2.1 and the dense indexes required by D8.2.4. The pass manager owns pass sequencing and fact dependencies per D8.2.5.

### 9.3 Split MirTranspiler by lifetime

The 108-field `MirTranspiler` is primarily several lifetimes placed in one struct:

- compilation/module lifetime
- function lifetime
- lexical-scope lifetime
- current expression/control-flow lifetime
- frame/rooting lifetime
- language-extension lifetime

Move these to `MirModuleEmitter`, `MirFunctionEmitter`, `MirFrameState` and typed side tables. Existing `MirEmitter`/`MirFrameState` shared structures should be reused and promoted where necessary; no static helper or state shape is copied into a new file.

### 9.4 AST node convergence

D8.2.2 already rules one LOOP/MATCH/IF/ASSIGN core node with syntax/form fields. Consolidate assignment variants and procedural loop variants behind those nodes. Keep pure Lambda `AST_FOR` distinct, as the same ruling explicitly requires.

After the unified source index is available, replace retained per-node `TSNode` with `SourceSpan` plus the dense `NodeId`. CST access remains compilation-unit-owned during the build phase rather than embedded in every post-build AST node.

## 10. Structures that must not be merged

| Structures/mechanisms | Ruling | Required treatment |
|---|---|---|
| String / Symbol / Binary | D2.1.3 | retain distinct tagged-leaf semantics and lifecycles |
| boxed Array / native Array / ArrayNum | D2.6.1 | retain three physical forms; share `StorageDesc` and semantic operations |
| Range / List / Array | S5.3.1 | one semantic sequence family does not imply identical storage structs |
| Map / Object | S5.4.2 | share `RecordStorage`; retain distinct semantic TypeIds/contracts |
| VMap / Map, future VArray/Array and VElement/Element | D7.4.5 | virtual carriers remain a separate dispatch/lifecycle mechanism |
| `Type*` / lowering representation / `MirValue` / MIR register type | D2.4.1 | keep separate authorities; delete only mirrored/recovered facts |
| MarkReader / MarkBuilder / MarkEditor | D7.1.5 | share Input storage authority, retain distinct capabilities/layers |
| language error / native system fault | D1.4v3 | explicit error completion remains distinct from recovery-frame faults |

## 11. Implementation stages

### P0 — Baseline and enforcement

1. Record the current census artifacts and native-slice measurements.
2. Add/verify ABI assertions for `Item`, `Container`, Function, Map/Object/Element and the frozen Context prefix.
3. Add a lightweight duplicate-authority checklist to code review: every new cached field names its canonical source and invalidation boundary.
4. Establish green `make build` and `make test-lambda-baseline` baselines before edits.

Acceptance: no behavior change; census and tests reproduce.

### P1 — Return-family deletion

1. **Done (P1.1, 2026-09-01):** delete the thirteen unused typed `Ret*` records, helpers and registry exports.
2. Migrate active `RetItem` system functions to boxed `Item` completion in coherent groups.
3. Delete `C_RET_RETITEM`, interpreter aggregate dispatch and MIR wrappers after the last user moves.
4. Consolidate return planning into `FnAbiContract` without changing the companion-lane ABI.

P1.1 acceptance: the thirteen obsolete typed records have no definition,
constructor, registry export, or dedicated test. `RetItem` migration and its
aggregate-return dispatch remain P1.2 work; error payloads and wide-scalar
tests remain green.

### P2 — Source and parser working sets

1. Introduce `SourceId`, `SourceSpan` and `SourceIndex`.
2. Migrate parser/runtime diagnostics and stack frames.
3. Replace fixed line/link/anchor arrays with dynamic storage.
4. Remove the duplicate `SourceLocation` names/types.

Acceptance: no fixed parser limits; markup parser fixed size below the agreed budget; large-line/link/anchor regression inputs pass.

### P3 — StorageDesc and shape authority

1. Introduce the one shared `StorageDesc` resolver and route existing consumers through it.
2. Revise D3.4.1/D3.4.2 and the shape design ledger as required by rule 17.
3. Introduce immutable `ShapeField[]`/`Shape` and migrate the pool.
4. Replace fixed `ShapeBuilder` arrays with full-contract dynamic drafts.
5. Move lookup, transitions and mutable JS caches to side structures.

Acceptance: one shape authority; full-contract nullable/union/constrained cases have layout tests; direct JIT and runtime field access agree byte-for-byte.

### P4 — Type graph consolidation

1. Introduce the canonical type-node header/domain split.
2. Remove `TypeType` and `lit_type` duplication.
3. Replace scalar-literal subclasses with `TypeLiteral`.
4. Shrink TypeMap/TypeElmt/TypeObject into thin semantic record types referencing `Shape`.

Acceptance: no wrapper unwrapping remains; type equality/reflection/inference/validator suites pass; `Type*` is the only semantic contract authority.

### P5 — Canonical record storage and C ABI layouts

1. Introduce `RecordStorage` and `SequenceStorage` accessors without changing offsets.
2. Migrate Map/Object/Element logic to the shared bodies.
3. Move the POD declarations to one C-compatible header.
4. Migrate C++ `Item`/`ConstItem` behavior to accessors/views, then use one `Item` typedef.

Acceptance: one physical declaration per ABI layout; C and C++ offset/size assertions pass; MIR direct-access tests pass.

### P6 — EvalContext ownership

1. Name/embed the frozen `EvalAbiContext` prefix.
2. Move heap/name/type/scheduler ownership solely to `EvalContext`.
3. Remove Runtime mirrors and bootstrap contexts.
4. Retire `input_context` from IO allocation paths.
5. Move optional subsystem state into non-reallocating lazy capsules.

Acceptance: exactly one evaluation TLS root and one owner for every isolate resource, matching D5.4.1–D5.4.2.

### P7 — Callable metadata

1. Introduce `FunctionCode`, `FunctionValue`, `FnAbiContract` and `FnEffects`.
2. Route TypeMethod and SysFunc metadata through the common callable authority.
3. Remove mirrored Function return/ABI flags and, after context migration, per-value runtime context pointers.

Acceptance: function equality still uses static site plus captures (S5.5.1); closure tracing and dynamic dispatch remain green.

### P8 — Compilation-unit and binding facts

1. Make `CompilationUnit` composition authoritative; stop growing `Script`/`Transpiler` inheritance.
2. Assign dense Binding IDs and move facts into pass-owned tables.
3. Split `MirTranspiler` by module/function/frame lifetime.
4. Converge core AST node variants per D8.2.2.

Acceptance: no lowering pass repairs binding or reconstructs representation; each pass declares required/produced facts per D8.2.5.

### P9 — Ratchets and close-out

1. Run a full struct census and compare counts/sizes/field counts with P0.
2. Add size budgets for small canonical records and fixed parser footprints.
3. Add lint/checks for duplicate ABI record names and forbidden old types.
4. Remove compatibility accessors only after repository-wide call-site migration.
5. Run `make lint`, `make test`, and release-build performance comparisons for hot-layout changes.

## 12. Proposed quantitative gates

These are target budgets, not formal semantics. Adjust only with measured evidence.

| Target | Gate |
|---|---:|
| typed/boxed `Ret*` structs | 0 |
| `SourceLocation` representations | 0; one `SourceSpan` mechanism |
| `ShapeBuilder` fixed size | <= 64 bytes excluding dynamic backing |
| `RecordType`/replacement for common `TypeMap` | <= 64 bytes excluding shared Shape/index/caches |
| per-parser embedded line/link/anchor capacity | 0 bytes |
| `MarkupParser` fixed footprint | < 16 KiB |
| owners of heap/name pool/type registry/scheduler per isolate | 1 each (`EvalContext`) |
| authorities for function return shape/transport | 1 (`FnAbiContract`) |
| C/C++ physical declarations for each public ABI record | 1 |
| pass-specific facts embedded in canonical `BindingDecl` | 0 |

Raw definition count is a secondary metric. Splitting a god struct into several pass-owned fact records can increase the count while reducing coupling, instance size and invalidation bugs.

## 14. Risks and mitigations

- **R1 — Shape ABI drift.** Runtime packed access and emitted direct access can disagree. Mitigation: one `StorageDesc` resolver, shared offset helpers, ABI asserts and byte-level cross-path tests.
- **R2 — Type-graph migration reads old nodes through the new header.** Mitigation: staged constructors, checked compatibility accessor and a temporary node-version/assertion gate.
- **R3 — Literal pointer ownership becomes ambiguous.** Mitigation: `TypeLiteral.Item` accepts only canonical inline values or payloads owned by the type/Input lifetime; wide-scalar/date-time ownership tests are mandatory.
- **R4 — Dynamic parser tables trade stack size for allocation failures.** Mitigation: allocator-owned ArrayList/HashMap structures, explicit failure diagnostics and adversarial large-input tests.
- **R5 — Removing inline TypeMap indexes regresses property lookup.** Mitigation: attach one lazily/canonically built `ShapeLookup` to shared shapes; benchmark release builds before deleting a hot index path.
- **R6 — JS mutable state leaks back into shared shapes.** Mitigation: immutable `JsClassMeta` only on shared type/family descriptors (D3.4.7); context-owned caches keyed by stable shape identity.
- **R7 — Context ownership migration creates transient double-free or dangling TLS state.** Mitigation: move one resource at a time, assert sole ownership and destroy through `EvalContext` only before deleting the mirror.
- **R8 — Function metadata sharing breaks closure identity or GC tracing.** Mitigation: immutable `FunctionCode`; captures remain per `FunctionValue`; retain explicit `closure_field_count` until tracing metadata is proven equivalent.
- **R9 — Fact tables become unsynchronized.** Mitigation: D8.2.5 pass manager declares producers/consumers; facts are immutable after their producing pass and indexed by stable IDs.
- **R10 — Clean-up turns into semantic flattening.** Mitigation: the non-consolidation table is a mandatory review gate; cite the applicable S#/D# ruling in every implementation PR.

## 15. Completion criteria

The campaign is complete when:

1. Every runtime fact has one named authoritative owner and derived mirrors are eliminated or mechanically generated.
2. Type values are direct canonical `Type*` graph nodes with no `TypeType`/`lit_type` parallel representation.
3. Record layout is owned by immutable shared `Shape`/`ShapeField` plus one `StorageDesc` resolver.
4. Map/Object/Element share one physical record-storage definition without losing semantic distinctions.
5. Public failures use boxed `Item`; generated native returns use only the formal companion-lane contract; no `Ret*` remains.
6. `EvalContext` is the sole owner of isolate runtime resources and the sole evaluation TLS identity.
7. Callable ABI facts live in one `FnAbiContract`; function values contain only code reference plus value-specific closure data.
8. Parser fixed footprint is independent of document line/link/anchor counts and diagnostics use one `SourceSpan` mechanism.
9. Compiler bindings and nodes use stable IDs with pass-owned fact tables; `VarEntry`/`MirTranspiler` no longer serve as cross-pass bags.
10. The full test suite, lint, ABI assertions, struct census and relevant release performance gates pass.

The architectural result is deliberately modest: fewer mechanisms, smaller common records, explicit ownership, and semantic distinctions preserved exactly where the formal specifications require them.
